# Zig Book Updater

## Purpose

Keep this book aligned with the current stable Zig language while staying useful to people who are completely new to Zig. Teach the current, recommended way to do work. Do not turn chapters into migration notes unless the user explicitly asks for a migration appendix.

## Source Layout

- `book.js` is generated locally and in CI. Do not edit it directly or commit it.
- `src/book_data.zig` is the typed table of parts and chapters.
- `content/chapters/*.html` contains chapter bodies.
- `src/runtime-prefix.js` contains browser helpers and content-authoring functions such as `z`, `sh`, `note`, `warn`, `tip`, and `danger`.
- `src/runtime-suffix.js` contains routing, rendering, sidebar, TOC, search, and theme behavior.
- `index.html` is the static shell and styles.
- `dist/` is the ignored publish directory generated by `zig build site`.
- `zig build serve` rebuilds `dist/` and serves it locally; pass `-Dport=8081` to override the default port.
- `.github/workflows/pages.yml` publishes `dist/` to GitHub Pages.

## Update Workflow

1. Read `AGENTS.md`, `src/book_data.zig`, and the relevant chapter files.
2. For Zig-version-sensitive claims or examples, run the research checklist below. Do not guess language rules, builtin behavior, standard-library signatures, or build-system API shapes.
3. Edit chapter prose in `content/chapters/*.html`.
4. When adding/removing/reordering chapters, update `src/book_data.zig` and the cover stats in `content/chapters/001-cover.html`.
5. Regenerate the site with `zig build generate`.
6. Build the publishable folder with `zig build site`.
7. For local development, serve the generated site with `zig build serve`.
8. Validate with `zig build check`.

## Stable Release Audit

Use this sequence before changing version targets, language-reference coverage, stdlib coverage, build-system chapters, or API examples:

1. Confirm the active compiler:
   - `zig version`
   - `zig env`
2. Confirm the official release state:
   - `https://ziglang.org/download/index.json`
   - `https://ziglang.org/download/`
   - Current stable release notes, for example `https://ziglang.org/download/0.16.0/release-notes.html`
3. Prefer the official stable release for book examples. Treat `master` and development builds as research input only until a tagged stable release appears in official download metadata and the local compiler is updated.
4. Read the official docs for the stable target:
   - Language reference: `https://ziglang.org/documentation/0.16.0/`
   - Standard library docs: `https://ziglang.org/documentation/0.16.0/std/`
   - Learn index: `https://ziglang.org/learn/`
   - Build system guide: `https://ziglang.org/learn/build-system/`
   - Overview, Getting Started, Samples, and Tools pages under `https://ziglang.org/learn/`
5. Use the installed stdlib source as the source of truth for signatures:
   - `STD_DIR=$(zig env | sed -n 's/.*\\.std_dir = "\\([^"]*\\)".*/\\1/p')`
   - `rg "pub fn name|pub const Type" "$STD_DIR"`
   - Inspect the actual files under `$STD_DIR`, especially `std.zig`, `Io.zig`, `process.zig`, `array_list.zig`, and module-specific directories.
6. Use docs for navigation and links:
   - Local browser docs: `zig std`
   - Official source repository: `https://codeberg.org/ziglang/zig`
7. For any nontrivial code example, compile or test a scratch file with the target Zig version before publishing the example. Remove scratch files afterward.

## Language Change Coverage

When the stable Zig version changes, audit the book against official sources before updating prose:

- Language reference: comments/doc comments, identifiers and `@""`, source encoding, operators, precedence, destructuring, `opaque`, casts, coercions, peer type resolution, zero-bit types, result-location semantics, compile variables, compilation model, keyword reference, style guide, builtins, async/concurrency status, atomics, packed structs/unions, error unions, optionals, comptime, generics, and test syntax.
- Standard library: top-level `std.zig` exports, allocator APIs, `std.Io`, filesystem APIs, process APIs, containers, JSON/ZON, crypto, testing, debug, logging, threading, atomics, networking, time, unicode, and build-system-facing helpers.
- Build system: standard target/optimize options, user options, options modules, tests, static and dynamic libraries, generated files, embedded assets, generated Zig source, C/C++ interop, system libraries, package dependencies, and multi-target release builds.
- Tooling and project workflow: `zig build`, `zig test`, `zig fmt`, `zig env`, `zig std`, `zig fetch`, `zig translate-c`, editor/LSP notes, and local dev serving for this site.

For each release audit, search the chapter sources for the previous version string and version-sensitive terminology:

```sh
rg -n "0\\.16\\.0|0\\.16|master|development build|deprecated|legacy|old way|pre-[0-9]|@cImport" content/chapters src/book_data.zig
```

Update the search pattern to include the old stable version when moving to a newer stable release. Generated files may be checked after regeneration, but never edited directly.

## Beginner-First Authoring

- Teach only the current stable approach in beginner-facing chapters.
- Avoid phrases like "the old way", "legacy", "deprecated", "previously", "used to", "renamed", or "migration" unless the section is explicitly a migration appendix requested by the user.
- Do not include obsolete code snippets as contrast examples. They distract new Zig users and make the current path harder to remember.
- If a release changed an API, state the current rule directly and link to official stable docs or release notes only when the extra context helps.
- Prefer small, active-project examples: CLI tools, config parsing with JSON/ZON, packages with tests and build options, C interop through build steps, and WASM or cross-target builds where relevant.
- Keep external practice resources as guidance for progression, not as sources of version-sensitive facts. Use Zig Learn, the stable language reference, stable std docs, release notes, and installed stdlib source for facts.

## Stdlib Map Maintenance

- Keep `content/chapters/040-stdlib-map.html` aligned with the public names in `std.zig` and the module files under `$STD_DIR`.
- When the stable Zig version changes, refresh the stdlib map from the new installed std tree and update links from `/0.16.0/` to the new stable version.
- Teach the stable public module names that new projects should reach for. Keep compatibility-only aliases out of beginner-facing prose unless they are still the official stable entrypoint.
- When adding a stdlib module to the map, include what it is for, when to reach for it, and where the deeper chapter or official docs/source live.

## Authoring Rules

- Chapter files are inserted into JavaScript template literals. Avoid raw backtick characters in prose; use `<code>...</code>` for inline code.
- Use `${z(\`...\`)}` for Zig examples, `${sh(\`...\`)}` for shell examples, and `note`/`warn`/`tip`/`danger` callouts for structured guidance.
- Keep code examples complete enough to compile when practical. For API examples, prefer the Zig 0.16 `std.process.Init` and `std.Io` shape used by the book.
- Keep generated output deterministic. If local `book.js` changes, it should be explainable from source changes plus `zig build generate`; it still must remain untracked.
- Do not hand-edit generated `dist/` files; rebuild them with `zig build site`.

## Verification Checklist

Run these before calling an update complete:

1. `zig build generate`
2. `zig build site`
3. `zig build check`
4. Compile or test every nontrivial new Zig example with the installed stable compiler.
5. If local preview matters, run `zig build serve` and smoke-check `http://127.0.0.1:8080/` or the selected `-Dport`.
6. Scan for beginner-hostile version-history phrasing after edits:
   - `rg -n "old way|pre-[0-9]|deprecated|legacy|previously|used to|renamed|migration|@cImport|master|development branch" content/chapters src/book_data.zig`
