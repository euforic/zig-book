Let's create a real project, run it, and dissect everything that happens. This is the shape every Zig project takes — single-file experiments to multi-million-line codebases all start here.

Scaffolding

Zig will generate a starter project for you:

${sh(`$ mkdir hello && cd hello $ zig init info: created build.zig info: created build.zig.zon info: created src/main.zig info: created src/root.zig info: see 'zig build --help' for a menu of options`)}

You get four files:

  • build.zig — the build script. Written in Zig, executed by zig build.
  • build.zig.zon — the manifest (name, version, dependencies, minimum Zig version).
  • src/main.zig — entry point for the executable.
  • src/root.zig — entry point for the library (you can ignore or delete it for now).

main.zig, simplified

The generated src/main.zig is a bit busy. Replace it with this minimal version while we learn:

${z(`const std = @import("std"); pub fn main() void { std.debug.print("Hello, Zig!\\n", .{}); }`)}

Build and run

${sh(`$ zig build run Hello, Zig!`)}

That command did two things. It compiled src/main.zig into an executable under zig-out/bin/, then ran it. If you just want the binary without running it:

${sh(`$ zig build $ ./zig-out/bin/hello Hello, Zig!`)}

Anatomy of every line

Now the autopsy. Each token in those four lines is doing real work.

const std = @import("std");

const declares an immutable binding. Zig requires const or var on every declaration — there is no implicit let. The right-hand side is a compile-time expression.

@import is a builtin: a compiler-provided function whose name starts with @. Builtins do things the language proper can't — query types, emit intrinsics, talk to the build system. @import("std") returns the standard library's root namespace as a value of type type. We bind that value to the name std.

This is not a special "import statement." It is an ordinary const declaration whose value happens to be a module. You could write const fs = @import("std").fs; and access fs.File directly.

pub fn main() void {

pub makes the function visible to other modules — including, importantly, the build system's startup code that calls it. Without pub, the symbol would be private to this file and you'd get a link error.

fn introduces a function. main is the conventional entry point. The parentheses hold the parameter list (empty here). void is the return type: this function returns no value.

You can also declare main with a return type of !void if it might fail (we'll meet error unions in Part V), or u8 to return an exit code. void means "succeeded silently."

std.debug.print("Hello, Zig!\\n", .{});

std.debug.print is a function — specifically, std.debug.print writes to standard error, never buffers, and is intended for debugging only. (Real output uses std.Io, which we'll cover in Part IX.) It takes two arguments: a format string and a tuple of arguments.

The "Hello, Zig!\\n" is a string literal, a slice of const u8 with a sentinel zero. The \\n is an escaped newline.

.{} is an anonymous empty struct literal — Zig's notation for a tuple with no fields. If we wanted to interpolate, we'd write something like:

${z(`std.debug.print("answer = {}\\n", .{42});`)}

The format string and the arguments are checked at compile time. Pass the wrong number or the wrong types and your build fails before a binary exists.

Looking at the build script

Open build.zig (we won't go deep here — Part X is dedicated to it):

${z(`const std = @import("std"); pub fn build(b: *std.Build) void { const target = b.standardTargetOptions(.{}); const optimize = b.standardOptimizeOption(.{}); const exe = b.addExecutable(.{ .name = "hello", .root_module = b.createModule(.{ .root_source_file = b.path("src/main.zig"), .target = target, .optimize = optimize, }), }); b.installArtifact(exe); const run_step = b.step("run", "Run the app"); const run_cmd = b.addRunArtifact(exe); run_step.dependOn(&run_cmd.step); }`)}

That's a Zig program that builds a Zig program. It declares an executable named hello rooted at src/main.zig, installs it to zig-out, and defines a custom run step. There is no separate build language; build.zig is real Zig with access to the standard library.

Build modes

Try compiling with different optimization profiles:

${sh(`$ zig build -Doptimize=Debug # default; safety checks on, no opt $ zig build -Doptimize=ReleaseSafe # opt + safety checks $ zig build -Doptimize=ReleaseFast # opt, safety checks off $ zig build -Doptimize=ReleaseSmall # opt for size`)}

Zig has four optimization profiles. Debug is the default; it gives you the fastest builds and the loudest safety checks. ReleaseSafe keeps the safety checks — overflow, bounds, null deref — while still optimizing. ReleaseFast drops them. ReleaseSmall optimizes for binary size. Pick deliberately.

What just happened, conceptually

You wrote a function in a language that has no runtime. The build script told the compiler to produce a static binary. The binary statically linked Zig's standard library (no shared libs are needed unless you ask for libc), called your main, wrote some bytes to file descriptor 2, and exited with status 0. That is the entire shape of a Zig program.

Try it: make the compiler teach you

Before moving on, make three intentional mistakes and read the diagnostics:

  1. Remove pub from main and run zig build run.
  2. Change the format string to "answer = {} {}\\n" but keep only one argument.
  3. Change const std to var std and notice how Zig treats mutable compile-time bindings.

Then restore the working version and add a tiny test file:

${z(`const std = @import("std"); pub fn meaning() u8 { return 42; } test "meaning is stable" { try std.testing.expectEqual(@as(u8, 42), meaning()); }`)} ${sh(`zig test src/main.zig`)}
