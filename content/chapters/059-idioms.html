You've made it through twelve parts. By now you can read most Zig code, write a multi-module project, manage memory deliberately, talk to C, and ship a cross-platform binary. This final chapter is a collection of idioms experienced Zig programmers reach for, and a list of where to look next to keep learning.

Idioms worth internalizing

Allocators are parameters

Take an allocator. Don't reach for a global. The function signature becomes self-documenting — "this function allocates" — and callers retain control.

${z(`pub fn loadConfig(allocator: std.mem.Allocator, path: []const u8) !Config { ... }`)}

defer is the deinit pattern

For every init there is a deinit. Pair them with defer right at the call site:

${z(`var list: std.ArrayList(u32) = .empty; defer list.deinit(allocator);`)}

errdefer for partial cleanup

${z(`pub fn create(io: std.Io, allocator: std.mem.Allocator) !*Resource { const self = try allocator.create(Resource); errdefer allocator.destroy(self); self.buffer = try allocator.alloc(u8, 1024); errdefer allocator.free(self.buffer); self.file = try std.Io.Dir.cwd().createFile(io, "data", .{}); return self; }`)}

Tagged unions for state machines

${z(`const State = union(enum) { idle, loading: struct { progress: f32 }, ready: []const u8, failed: anyerror, };`)}

Comptime as code generation

If you find yourself writing similar code five times with one varying type, lift it into a comptime function that returns a type. Generic containers, polymorphic algorithms, table-driven dispatchers all fall out of this.

Slices, not C pointers

Anywhere you'd write T* + length in C, use []T in Zig. You get length-checked iteration and clean APIs.

Error sets per layer

Don't pile every possible error into a single huge error set. Each layer of your code defines its own narrow error set; the next layer up either re-raises (with try inferring the set) or maps to its own.

Traps to avoid

Holding a slice across reallocation

${z(`var list: std.ArrayList(u32) = .empty; defer list.deinit(allocator); try list.appendSlice(allocator, &.{ 1, 2, 3 }); const view = list.items; // points into list's buffer try list.append(allocator, 4); // may reallocate \\u2014 view is now dangling std.debug.print("{}\\\\n", .{view[0]}); // UB`)}

The fix: either copy the data out, or don't mutate the list while a borrow exists.

Forgetting to capture optionals

${z(`// Wrong if (maybe_value != null) { const v = maybe_value.?; // works, but redundant } // Right if (maybe_value) |v| { // use v }`)}

Mixing comptime values into runtime data

A comptime_int or comptime_float is unbounded. When it ends up in a runtime expression, it has to coerce to a concrete type — often i64 or f64. If that's not what you want, annotate explicitly.

Comparing strings with ==

== on slices compares pointer and length, not contents. Use std.mem.eql(u8, a, b).

Treating C strings like Zig strings

A [*:0]const u8 from C has no length until you scan for the terminator. Use std.mem.span(cstr) to turn it into a real []const u8 before passing it to Zig APIs.

Performance habits

  • Profile before optimizing. Zig binaries play well with perf, Instruments, and VTune.
  • Try ReleaseFast for benchmarks; the difference vs Debug is usually 5\\u201320x.
  • Reach for @Vector when you have data-parallel arithmetic over chunks of 4, 8, or 16 elements.
  • Arena allocators win in request/response and frame-based workloads. Use them.
  • For hot paths, prefer iteration over recursion; the compiler can sometimes vectorize loops but rarely tail-calls.

Where to go next

Read the standard library

The Zig stdlib is small and readable. Whenever you wonder "how does Zig do X?" — open std/X.zig. The source is the documentation in the best sense: idiomatic, tested, and current.

Build something concrete

Pick a real problem. A toy language interpreter, a TCP echo server, a static site generator, an embedded firmware blinky. Build it end to end. Cross-compile it. Ship a release. The depth of understanding from one finished project exceeds anything from twenty tutorials.

Read other people's Zig

The Zig source itself is in Zig. Tigerbeetle, Bun, Mach engine, Ghostty terminal, and many more are public Zig codebases of substantial size. Read them with intent: how do they structure modules, name errors, organize tests, lay out build scripts?

Follow the language

Zig is pre-1.0 and the language evolves. Watch the release notes (one or two major releases per year, plus point releases). Each release has a write-up that explains the why behind each change — high-quality reading even if you skip the patch.

Keep a reference stack

For active work, keep three sources close: this book for the learning path, the official 0.16.0 language reference for exact semantics, and your installed std_dir for API truth. When those disagree with a blog post, trust the compiler and the source.

Keep practicing after the book

Use Ziglings when syntax is rusty, Exercism when you want repetition and feedback, and project-based material when you need a larger arc. The point is not more content consumption; the point is writing enough Zig that error handling, allocation, and build scripts become ordinary.

Participate

The Zig community lives on the official Discord, IRC, and the project's Codeberg discussions. Show up with a small, well-formed question or contribution; the people are warm and the bar for useful contribution is lower than you'd think.

Closing

Zig is a small language that asks you to be explicit about the things that matter — memory, time, errors, target — and gets out of your way for everything else. The reward for that explicitness is code that's easier to read at scale, easier to port to anything with a CPU, and easier to reason about under pressure. The reward for finishing this book is that you can write that code.

Go build something.
