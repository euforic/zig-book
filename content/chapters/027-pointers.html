Zig has more pointer types than C, and each one carries information the compiler uses to reject mistakes. The cost is a moment of mental overhead picking the right one; the benefit is that the pointer type itself documents what's at the other end.

*T — one of these

The single-item pointer is the everyday case. It points to exactly one value of type T. You dereference with .*:

${z(`var x: i32 = 42; const p: *i32 = &x; p.* += 1; // x is now 43 std.debug.print("{}\\n", .{p.*});`)}

A *T is guaranteed non-null. You cannot do pointer arithmetic on it, you cannot index it. It's just "one T over there."

[*]T — many of these, unknown count

The many-item pointer is a C-style raw pointer: it points to a sequence of T, with no length information. You index it, you do pointer arithmetic, you do not know where it ends.

${z(`extern fn c_strlen(s: [*:0]const u8) usize; const arr: [4]u8 = .{ 1, 2, 3, 4 }; const p: [*]const u8 = &arr; const third = p[2]; // 3`)}

Most Zig code uses []T (a slice — pointer plus length) instead. The many-item pointer mostly appears at C boundaries.

[*:s]T — sentinel-terminated

A many-item pointer where a known sentinel value marks the end. [*:0]const u8 is a C string:

${z(`const c_str: [*:0]const u8 = "hello"; // The compiler knows there's a 0 byte at index 5.`)}

Slices can have sentinels too: [:0]const u8 is a slice whose backing memory has a known terminator past the length.

[]T — slices

A slice is a struct: { ptr: [*]T, len: usize }. It's the default way to talk about "some Ts in a row." We covered slices in Part II; mention here because they're the most common pointer-shaped thing you'll handle.

${z(`fn sum(xs: []const u32) u32 { var total: u32 = 0; for (xs) |x| total += x; return total; }`)}

Const and address spaces

*const T is a read-only pointer. *T is read-write. The compiler will let you go read-write → read-only implicitly, never the other way.

${z(`fn read(p: *const i32) i32 { return p.*; } var x: i32 = 5; _ = read(&x); // ok: *i32 coerces to *const i32`)}

Alignment

Every pointer type carries an alignment. A *u32 is aligned to 4 bytes by default; the type signature says *align(4) u32 when written long. You can request looser alignment:

${z(`const bytes: [16]u8 align(4) = .{0} ** 16; const p: *const align(1) u32 = @ptrCast(&bytes[1]); // misaligned read const v = p.*;`)}

Misaligned access is allowed but the compiler will not assume natural alignment for code generation. Going the other direction — claiming more alignment than the data has — is undefined behavior caught by safe builds.

*anyopaque — type-erased pointer

The escape hatch. *anyopaque is a pointer to "I don't know what." You can't dereference it; you must cast it back to a concrete type first:

${z(`fn callback(ctx: *anyopaque, value: i32) void { const self: *MyContext = @ptrCast(@alignCast(ctx)); self.handle(value); }`)}

The pattern @ptrCast(@alignCast(ptr)) is the canonical way to recover a typed pointer from an opaque one. Use sparingly — type-erasure throws away safety.

?*T — optional pointer

A pointer that might be null. The compiler uses the all-zero bit pattern as the null encoding, so ?*T takes the same space as *T:

${z(`fn find(needle: u8) ?*const u8 { _ = needle; return null; } if (find('x')) |p| { std.debug.print("found at {*}\\n", .{p}); } else { std.debug.print("not found\\n", .{}); }`)}

This is the right choice for "maybe a pointer." Don't use a separate boolean to track validity — let the type system carry it.

Taking addresses

&x takes the address of x. The result's type depends on x:

  • &local_int → *i32
  • &array[2] → *u8 (or whatever element type)
  • &array → *[N]u8 (pointer to the whole array)
  • &function → *const fn (...) ...

Taking the address of a temporary is fine, but the temporary's lifetime ends with the expression — keep references shorter than the things they point to.
