Zig has a single, ruthless rule about memory: nothing allocates without an allocator parameter. The standard library, every third-party library, every function you write — if it needs heap memory, it takes an Allocator argument. There is no global heap, no new, no default behavior to leak around.

This rule makes Zig code, even Zig you've never seen before, easy to audit: scan for Allocator parameters and you've found every byte of potential heap traffic.

Where values live

Variables go on the stack by default. Compile-time-known values may live in read-only memory (the binary itself). Heap allocations are explicit, always:

${z(`var on_stack: [1024]u8 = undefined; // stack const literal = "hello"; // .rodata const heap = try allocator.alloc(u8, 1024); // heap (explicit) defer allocator.free(heap);`)}

There is no third option. No "boxed" type, no implicit moves, no garbage collector that might run.

The Allocator interface

An std.mem.Allocator is a fat pointer: a context pointer plus a vtable of function pointers. Implementations include general-purpose, arena, fixed-buffer, page, C-malloc, and several specialized ones. We'll cover them next chapter.

${z(`pub fn run(allocator: std.mem.Allocator) !void { const buf = try allocator.alloc(u8, 4096); defer allocator.free(buf); // ... use buf ... }`)}

The caller decides which allocator. Tests use std.testing.allocator (which catches leaks). Long-running services often use the general-purpose allocator. Short-lived request handlers often use an arena. Same function, three different memory strategies, zero changes to run.

Ownership without a borrow checker

Zig has no borrow checker. Ownership is a convention, communicated through documentation, parameter types, and discipline. The common rules:

  • If a function takes a slice []const u8, it borrows for the call only — don't keep it after.
  • If a function returns an allocated slice, the caller frees it.
  • If a function takes an Allocator, it may allocate; ownership of any returned allocation transfers to the caller.
  • Containers track their own allocations and free them in deinit.

None of this is enforced by the compiler. All of it is enforced by the GeneralPurposeAllocator's leak detector in debug builds.

undefined and uninitialized memory

You can leave a variable uninitialized by assigning undefined:

${z(`var buf: [256]u8 = undefined; const written = try writer.write(&buf);`)}

In safe builds, undefined fills the memory with 0xAA bytes so use-before-init bugs are loud. In fast builds, it's literally whatever was there. Read from undefined before writing and you have undefined behavior.

The stack is yours

Unlike many languages, Zig doesn't punish stack allocation. Multi-kilobyte stack buffers are common and idiomatic:

${z(`var path_buf: [std.Io.Dir.max_path_bytes]u8 = undefined; const n = try std.Io.Dir.cwd().realPathFile(io, "relative/thing", &path_buf); const path = path_buf[0..n];`)}

If you can fit it on the stack and the size is bounded, do. The allocator only enters the picture for unbounded or long-lived data.

Three flavors of "alloc"

The allocator interface gives you three primitives:

${z(`const p = try allocator.create(Point); // one T defer allocator.destroy(p); const buf = try allocator.alloc(u8, 1024); // many T (slice) defer allocator.free(buf); const huge = try allocator.alignedAlloc(u8, .@"4096", 1 << 20); // aligned slice defer allocator.free(huge);`)}

That's all you usually need. Higher-level helpers like dupe, realloc, and friends build on these three.
