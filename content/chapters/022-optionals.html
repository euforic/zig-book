An optional type, written ?T, holds either a value of type T or the special value null. Zig uses optionals everywhere you'd find nullable references in other languages — and the compiler enforces unwrapping before use, so the billion-dollar mistake is a compile error.

Declaring optionals

${z(`var maybe_age: ?u32 = null; maybe_age = 42; maybe_age = null; const found: ?[]const u8 = std.mem.indexOfScalar(u8, "abc", 'b'); // Wait — that returns ?usize. Let's correct: const idx: ?usize = std.mem.indexOfScalar(u8, "abc", 'b');`)}

Unwrapping

You can't use an optional value as if it were the wrapped type — you must unwrap. Four ways, each suited to a different situation.

1. if-capture

${z(`if (maybe_age) |age| { std.debug.print("You are {} years old.\\n", .{age}); } else { std.debug.print("Age unknown.\\n", .{}); }`)}

The capture syntax binds the inner value if non-null. Inside the block, age has type u32.

2. orelse

${z(`const age = maybe_age orelse 0; const name = lookup(user_id) orelse "anonymous";`)}

orelse supplies a fallback value when the optional is null. The right-hand side has the wrapped type.

3. orelse with control flow

${z(`const file = openMaybe() orelse return error.NoFile; const config = readConfig() orelse { std.log.warn("no config; using defaults", .{}); break :blk default_config; };`)}

The right side of orelse can be a control-flow expression (return, continue, break, or a labeled block) — it just needs to be type noreturn or the wrapped type.

4. .? — the unwrap assertion

${z(`const age = maybe_age.?; // panics if maybe_age is null`)}

Equivalent to maybe_age orelse unreachable. Use only when you can prove the value is non-null. In safe builds it panics with a useful message; in ReleaseFast it's UB.

while on optionals

Looping while an optional remains non-null is idiomatic Zig:

${z(`var iter = list.iterator(); while (iter.next()) |item| { process(item); }`)}

This loop runs as long as iter.next() returns a non-null value, automatically unwrapping it.

Optional pointers

The type ?*T is the type of "a pointer that might be null." For a non-optional pointer (*T), the compiler guarantees non-null at the type level — you cannot assign null to a *T.

${z(`fn find(haystack: []const u8, needle: u8) ?*const u8 { for (haystack) |*c| { if (c.* == needle) return c; } return null; }`)}

This is a powerful guarantee: any function that takes a *T doesn't have to defensively null-check.

${tip("Niche layout", "

An ?*T takes the same space as a *T — the all-zero pointer encodes null. Same for slices (?[]T), function pointers, and any type with an obvious sentinel.

")}

Optional chaining

Zig has no ?. operator. You unwrap deliberately at each step:

${z(`fn getCity(user: ?User) ?[]const u8 { const u = user orelse return null; const addr = u.address orelse return null; return addr.city; }`)}

Verbose, but every potential null is visible. With a labeled block you can compress it:

${z(`fn getCity(user: ?User) ?[]const u8 { return blk: { const u = user orelse break :blk null; const addr = u.address orelse break :blk null; break :blk addr.city; }; }`)}

Optionals in function returns

Use ?T when "missing" is a normal outcome that the caller will handle (e.g. "not found"). Use !T when missing is a failure (e.g. "couldn't open file"). The distinction is semantic but matters at call sites:

${z(`fn lookup(name: []const u8) ?*User { _ = name; return null; } // optional fn read(file: []const u8) ![]u8 { _ = file; return error.IoFail; } // error union const user = lookup("alice") orelse return error.UserNotFound; const data = try read("config");`)}
