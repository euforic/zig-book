Zig's generics are not a separate feature. They are the natural consequence of type being a value: a generic function is just a function with a comptime T: type parameter, and a generic type is a function that returns a type.

Generic functions

A function that works for any T:

${z(`fn max(comptime T: type, a: T, b: T) T { return if (a > b) a else b; } const m1 = max(i32, 3, 7); // 7 const m2 = max(f64, 1.5, 2.5); // 2.5 const m3 = max(u8, 'a', 'z'); // 'z'`)}

Each call site specializes the function for its T. The compiler emits separate code for each instantiation, like C++ templates, but the source is just Zig.

Inferring the type

It would be tedious to write max(i32, ...) every time. Use anytype to let the compiler infer:

${z(`fn max(a: anytype, b: @TypeOf(a)) @TypeOf(a) { return if (a > b) a else b; } const m = max(3, 7); // i32 by default const f = max(@as(f64, 1.5), 2.5);`)}

anytype means "any type, inferred from the argument." @TypeOf(a) reads the inferred type back out. This is the idiomatic shape of polymorphic helpers in the stdlib.

Generic types

A function returning a struct produces a generic container:

${z(`fn Stack(comptime T: type) type { return struct { items: []T, len: usize, const Self = @This(); pub fn init(allocator: std.mem.Allocator, capacity: usize) !Self { return .{ .items = try allocator.alloc(T, capacity), .len = 0, }; } pub fn push(self: *Self, value: T) !void { if (self.len >= self.items.len) return error.Overflow; self.items[self.len] = value; self.len += 1; } pub fn pop(self: *Self) ?T { if (self.len == 0) return null; self.len -= 1; return self.items[self.len]; } }; } const IntStack = Stack(i32); const StrStack = Stack([]const u8);`)}

Two essential idioms here. @This() inside a struct evaluates to the struct type itself; aliasing it to Self keeps methods readable. And calling Stack(i32) at module top-level is fine — it runs at comptime and produces a concrete type you can use anywhere.

The type-as-namespace trick

Because the struct returned by a generic-type function captures its comptime arguments, you can reference them throughout its methods. They become "type parameters" without any special syntax:

${z(`fn Buffer(comptime T: type, comptime N: usize) type { return struct { data: [N]T = undefined, len: usize = 0, const Self = @This(); pub fn push(self: *Self, x: T) !void { if (self.len >= N) return error.Full; self.data[self.len] = x; self.len += 1; } }; } const Buf16 = Buffer(u8, 16);`)}

Inside push, N and T are still in scope — they're comptime parameters of the surrounding function. The compiler bakes them into the generated code.

Constraints with comptime checks

Zig has no trait system. To constrain a type, you write a check in comptime that @compileErrors if the type doesn't satisfy it:

${z(`fn requireIterator(comptime T: type) void { if (!@hasDecl(T, "next")) @compileError(@typeName(T) ++ " has no next() method"); } fn consume(iterator: anytype) void { requireIterator(@TypeOf(iterator)); while (iterator.next()) |item| process(item); }`)}

This is duck typing with a clear error message. Less expressive than traits, more flexible in everyday code.

Caching: same args → same type

Zig caches type-returning function calls. Stack(i32) called twice yields the same type, not two different types that happen to be equivalent:

${z(`comptime { std.debug.assert(Stack(i32) == Stack(i32)); // true, same type }`)}

This means you can use generic instantiations as keys, store them in tables, compare them — they're stable.

The Iterator pattern

The stdlib uses a consistent shape for iterators:

${z(`pub fn Iter(comptime T: type) type { return struct { items: []const T, idx: usize = 0, const Self = @This(); pub fn next(self: *Self) ?T { if (self.idx >= self.items.len) return null; defer self.idx += 1; return self.items[self.idx]; } }; }`)}

Any type with a next() ?T method is an iterator. Range-friendly with while (it.next()) |x|. No interface declaration, no opt-in — just the shape.
