Zig was designed from day one to consume C. You can translate C headers into a Zig module, call C functions, compile C source files, and pass ABI-compatible values across the boundary without hand-writing a full binding layer.

Translate C headers in build.zig

C-translation is a build-system step: std.Build.Step.TranslateC. You declare the headers you want translated; the build system runs the translator, caches the output by content hash, and exposes the result as a normal Zig module.

${z(`// build.zig const translate_c = b.addTranslateC(.{ .root_source_file = b.path("src/c_headers.h"), .target = target, .optimize = optimize, }); translate_c.addIncludePath(b.path("vendor/include")); translate_c.defineCMacroRaw("FEATURE_FOO=1"); const c_mod = translate_c.createModule(); const root = b.createModule(.{ .root_source_file = b.path("src/main.zig"), .target = target, .optimize = optimize, }); root.addImport("c", c_mod); const exe = b.addExecutable(.{ .name = "app", .root_module = root }); exe.linkLibC();`)}

Your src/c_headers.h contains the C #include directives for the translated module:

${code('c', `#include #include #include `)}

In your Zig source:

${z(`const c = @import("c"); pub fn main() void { _ = c.printf("translated: %d\\\\n", @as(c_int, 42)); }`)} ${note('Why this is better. The build graph now sees C-translation as a normal step, so cache invalidation is correct: change a header and only translation reruns; the Zig code itself doesn\\u2019t re-translate. You can also inspect the generated Zig file under .zig-cache — invaluable when debugging FFI issues.')}

Linking against C libraries

${z(`exe.linkLibC(); // link against the system libc exe.linkSystemLibrary("z"); // -lz (zlib) exe.linkSystemLibrary("ssl"); // -lssl // Link a local static archive exe.addObjectFile(b.path("vendor/libfoo.a")); // Add include paths and source files for a bundled C library exe.addIncludePath(b.path("vendor/sqlite")); exe.addCSourceFile(.{ .file = b.path("vendor/sqlite/sqlite3.c"), .flags = &.{ "-DSQLITE_THREADSAFE=1", "-O2" }, });`)}

You can mix and match: link against a system library on Linux, compile the same library from source on Windows, all from one build.zig with a conditional.

Calling conventions and ABI

C functions are extern in Zig. Their calling convention is callconv(.c). Most translated functions are already extern; if you're declaring a C signature by hand:

${z(`extern "c" fn printf(fmt: [*:0]const u8, ...) c_int; pub fn main() void { _ = printf("answer: %d\\\\n", @as(c_int, 42)); }`)}

Variadic functions (the ...) work but every variadic arg must be explicitly cast to the C type. Zig doesn't do C's default argument promotions for you — that's a feature.

C types and Zig types

Zig defines C-compatible types whose sizes follow the target ABI:

  • c_char, c_short, c_int, c_long, c_longlong
  • c_uint, c_ushort, c_ulong, c_ulonglong
  • c_float, c_double, c_longdouble
  • [*c]T — a C pointer (allows null, allows aliasing rules C expects). Prefer ?*T or [*]T in pure Zig code; [*c] exists for translated code.

Strings across the boundary

C strings are null-terminated. Zig represents them as [*:0]const u8 (pointer-to-many, sentinel-terminated by 0). String literals in Zig are already [:0]const u8 — they're zero-terminated as a courtesy. So "hello" passes to C unchanged.

${z(`const c = @import("c"); const path: [*:0]const u8 = "/etc/hosts"; const f = c.fopen(path, "r"); if (f == null) return error.OpenFailed; defer _ = c.fclose(f);`)}

What translate-c can't handle

The translator handles the bulk of typical headers, but some C constructs are too dynamic or context-dependent. Function-like macros that expand to expressions are typically not translated; structs with unnamed bitfields can be tricky; _Generic selections don't translate. The fallback is to write a small wrap.c file with explicit functions that wrap the macros, compile it into your build, and call the wrappers from Zig.
