An enum in Zig is a type whose values are a finite set of named tags. The tags can have explicit integer values; the type can have methods. Compared to C-style enums, Zig's are namespaced, exhaustively switchable, and resistant to silent integer arithmetic.

Basic enum

${z(`const Color = enum { red, green, blue }; const c: Color = .red; const c2 = Color.green; std.debug.print("{s}\\n", .{@tagName(c)}); // "red"`)}

Tags are accessed by namespace (Color.red) or, when the type is known from context, by the .tag shorthand.

Tag values

You can specify the underlying integer type and per-tag values:

${z(`const Status = enum(u8) { ok = 0, not_found = 404, server_error = 500, }; const s: Status = .not_found; const code: u8 = @intFromEnum(s); // 404 const back: Status = @enumFromInt(@as(u8, 500)); // .server_error`)}

The backing integer can be any integer type. If you don't specify, Zig picks the smallest unsigned type that fits all tags.

Switching on enums

Exhaustive matching is the typical use case:

${z(`fn name(c: Color) []const u8 { return switch (c) { .red => "red", .green => "green", .blue => "blue", }; }`)}

Add a tag and every existing switch will fail to compile until you handle it. This is one of the great pleasures of Zig.

Methods on enums

${z(`const Direction = enum { north, east, south, west, pub fn opposite(self: Direction) Direction { return switch (self) { .north => .south, .south => .north, .east => .west, .west => .east, }; } pub fn isVertical(self: Direction) bool { return self == .north or self == .south; } }; const d: Direction = .north; const o = d.opposite(); // .south const v = d.isVertical(); // true`)}

Non-exhaustive enums

An enum declared with _ as a final tag is "open" — values outside the named tags are valid:

${z(`const HttpStatus = enum(u16) { ok = 200, not_found = 404, server_error = 500, _, }; const future: HttpStatus = @enumFromInt(@as(u16, 418)); switch (future) { .ok, .not_found, .server_error => {}, _ => std.debug.print("unknown status\\n", .{}), }`)}

Use these for things like syscall numbers or HTTP statuses where the spec is open-ended.

Enums and integer literals

You cannot mix enum values and integers without explicit conversion. Adding 1 to a Color is not a thing; you must @intFromEnum first if that's really what you want.

Implicit enum literals

When the expected type is an enum, you can write just the dot-prefixed tag name:

${z(`fn setColor(c: Color) void { _ = c; } setColor(.red); // .red infers as Color.red const arr = [_]Color{ .red, .green }; // each .red infers from the array type`)}

This makes enum-heavy code dramatically less noisy than C-style fully qualified names.

The errortype family

Zig's error sets are a kind of enum — see Part V. The connection is more than cosmetic; under the hood, an error value is an integer index into a global error table.
