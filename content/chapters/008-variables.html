Every binding in Zig is declared with either const or var. There is no implicit declaration, no shadowing without a new keyword, no untyped temporaries with surprising rules. Two keywords, both opinionated.

const

const introduces an immutable binding. Once initialized, the value (or, for pointers, the pointer) cannot change.

${z(`const greeting = "Hello"; const max_users: u32 = 1024; const pi: f64 = 3.141592653589793; greeting = "Howdy"; // error: cannot assign to constant`)}

You can omit the type when Zig can infer it. You're encouraged to write it when it adds clarity, especially for numeric literals where the inferred type might surprise you (more on that in the next chapter).

var

var introduces a mutable binding. The value can be reassigned. The type must be known at compile time, but you can defer initialization within a block.

${z(`var counter: i32 = 0; counter += 1; counter = 42; var name: []const u8 = undefined; name = "Andrew";`)}

undefined

undefined is a value of any type that means "uninitialized." In Debug and ReleaseSafe builds, reading undefined memory tries to detect the mistake — most types are filled with 0xAA bytes so the values look obviously broken in a debugger. In ReleaseFast, the memory is whatever was there. Never depend on the value.

${danger("Trap", "

Don't conflate undefined with null. null is a real value (of optional types); undefined is a hole in your program that you've promised to fill before reading. Reading an undefined integer is undefined behavior, not a defined sentinel.

")}

Mutability is shallow

This catches people coming from Rust. A const binding to a struct that contains a slice does not freeze the slice's elements:

${z(`const std = @import("std"); pub fn main() void { var buf = [_]u8{ 1, 2, 3 }; const slice = buf[0..]; // const slice ... slice[0] = 99; // ... but the bytes it points at are mutable std.debug.print("{any}\\n", .{buf}); // { 99, 2, 3 } }`)}

The const means "the slice value (pointer + length) cannot be reassigned." The pointed-to memory's mutability is part of the pointer's type: []u8 vs []const u8. We'll come back to this when we cover pointers.

Constants must be compile-time computable… unless they aren't

You can initialize a const with a runtime value:

${z(`fn now() i64 { return std.time.timestamp(); } pub fn main() void { const start = now(); // ok: const just means "no reassignment" std.debug.print("{}\\n", .{start}); }`)}

The literal "constant" meaning of const in Zig is "single-assignment binding," not "compile-time known." There is a separate concept for the latter — comptime — covered in Part VII.

Container-level declarations

A top-level declaration (one outside any function) is implicitly resolved at compile time. Such declarations can be const or var:

${z(`const std = @import("std"); const MAX_LEN: usize = 1024; var global_count: u32 = 0; // file-level mutable; threadlocal? no, plain global fn bump() void { global_count += 1; }`)} ${warn("Globals are globals", "

A top-level var is a real mutable global. Multi-threaded code sharing it without synchronization is a data race. Use threadlocal var for per-thread state, or move state into a struct you pass around. Most Zig code avoids globals.

")}

Visibility: pub vs private

By default, declarations are private to the file. Prefix with pub to expose them to other modules.

${z(`// math.zig pub const PI = 3.14159265358979; const SECRET_SALT = 0xDEADBEEF; // not exported pub fn area(r: f64) f64 { return PI * r * r; }`)}

This is purely a visibility marker; it doesn't change linkage or codegen. A non-pub function can still be called from a pub function in the same file.

Shadowing is not allowed

Zig refuses to let you redeclare the same name in a nested scope:

${z(`fn confusing(x: i32) i32 { var x: i32 = 5; // error: redefinition of 'x' return x; }`)}

This is intentional. The compiler would rather make you choose a different name than allow the kind of bug where you think you're modifying the outer x but you've quietly created an inner one.

Type inference and explicit types

For locals, the right-hand side type is usually obvious. For function parameters and struct fields, types are required. For numeric literals, types are determined by the context they flow into; we'll spend the next chapter making that precise.

One last detail before we leave: unused variables are errors, not warnings. Discard with _:

${z(`const result = computeExpensiveThing(); _ = result; // ok, intentionally unused`)}
