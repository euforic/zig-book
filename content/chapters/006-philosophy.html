Most of Zig's design choices follow from a small set of beliefs. If you internalize them, the rest of the language stops looking like a list of rules and starts looking like the consequence of taking one or two ideas very seriously. This chapter is about those ideas.

1. No hidden control flow

In Zig, control transfers happen only at constructs you can see. The list is short:

  • Function calls
  • if / else
  • switch
  • while / for
  • break / continue / return
  • try / catch (which are visible error propagation)
  • defer / errdefer (which run at scope exit you can see)

That's all. There are no exceptions that unwind invisibly. There are no destructors. There is no operator overloading, so a + b calls no method. There are no implicit conversions; @as, @intCast, @floatCast, @ptrCast are explicit. There are no implicit constructors that run when a value is created. Reading Zig is reading exactly what runs.

2. No hidden allocations

The standard library never calls the system allocator on its own. Any function that needs heap memory takes an Allocator as a parameter. You pass in the allocator you want — the general-purpose allocator, an arena, a fixed buffer, a custom pool — and you can swap implementations without changing the function.

${z(`var gpa: std.heap.GeneralPurposeAllocator(.{}) = .init; defer _ = gpa.deinit(); const allocator = gpa.allocator(); const buf = try allocator.alloc(u8, 1024); defer allocator.free(buf);`)}

Two consequences. First, you always know which line allocates — it's the one that takes an allocator. Second, you can test a function that uses heap memory with a leak-checking allocator and detect every leak at unit-test time.

3. Errors are values

A function that can fail has a return type like !T — short for "either an error or a T". The compiler refuses to let you drop the error case. You either handle it (catch), propagate it (try), or convert it (orelse, error.SomeError in a switch).

${z(`fn readConfig(io: std.Io, allocator: std.mem.Allocator) ![]u8 { const cwd = std.Io.Dir.cwd(); return try cwd.readFileAlloc(io, "config.toml", allocator, .limited(1 << 20)); }`)}

Errors have no stack traces in the type, no payload, no inheritance. They're tagged enum values. They cost a register at the ABI level. They cannot be silently ignored. We dedicate Part V to them.

4. Comptime is the metaprogramming system

Most languages have one syntax for runtime code and a different one (templates, macros, decorators) for metaprogramming. Zig has one syntax for both. Functions can run at compile time. type is a first-class value. Generics are functions that take types as parameters and return types.

${z(`fn Stack(comptime T: type) type { return struct { items: []T, len: usize, pub fn push(self: *@This(), v: T) void { self.items[self.len] = v; self.len += 1; } }; } const IntStack = Stack(i32);`)}

Stack is a function. Called at compile time, it returns a struct type. The compiler caches the result, so Stack(i32) always refers to the same type. No template language; no separate macro DSL. Part VII covers this in depth.

5. Manual memory management

Zig does not have a garbage collector. It does not have Rust-style ownership and borrowing. It does not pretend to. You allocate memory; you free it. The language gives you tools — defer, error-aware errdefer, the allocator interface — but the bookkeeping is yours.

This is the most-debated design decision in Zig. The argument for it: most real C and C++ codebases manage memory correctly because they use arenas, pools, and clear ownership conventions, not because they have a borrow checker. Zig makes those conventions easy to express. The argument against: it's the 21st century and we should have automated this.

Either way, that's the bet Zig is making. We cover the playbook in Part VI.

6. Small language, big standard library

Zig has 22 keywords. The whole language reference fits in one HTML file. There is one composite "container" construct (the struct) that doubles as a namespace, a class, a tuple, and a module. There is one loop for iteration (for) and one for conditions (while). Everything else is functions and types.

The standard library, meanwhile, is broad: cryptography, compression, file system, networking, HTTP, JSON, formatting, generic containers, threads, atomics, fuzzing, debug-info parsing. It is also unstable — every release reorganizes some piece of it. We will mark this throughout the book.

7. Robust, optimal, reusable

The official tagline is three words: robust, optimal, reusable. Roughly:

  • Robust — programs behave correctly even when conditions are bad: out of memory, file missing, bit flipped, allocator misbehaving.
  • Optimal — the language gets out of the way and lets the program do exactly what's needed, no more.
  • Reusable — the same code works in different situations: embedded, kernel, userspace, WASM, freestanding.

Allocator parameters help with all three. So does avoiding hidden control flow. So does compile-time emulation of the target architecture, which lets the same code work on platforms with different pointer sizes and endianness.

What Zig is not

This list is shorter, but worth saying out loud:

  • Zig is not a safe language. It will not stop you from dereferencing freed memory. It gives you tools to catch the mistake at test time; it does not eliminate it at compile time.
  • Zig is not a high-level language. There is no built-in string class with methods; "hi" is a slice of bytes.
  • Zig is not an object-oriented language. There are no classes, no inheritance, no virtual dispatch (unless you build it yourself with tagged unions or vtables).
  • Zig is not Rust. The languages share the systems-programming niche, but they make different bets. If you need memory safety as a compile-time guarantee, use Rust. If you need a smaller, simpler language and are willing to take responsibility for memory, Zig has something to offer.
