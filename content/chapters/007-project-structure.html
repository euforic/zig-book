You'll meet zig build in every chapter from here on, so a working mental model now will pay dividends. We won't be exhaustive — Part X is dedicated to the build system — but you should leave this chapter able to read a typical build.zig and know which knobs do what.

The two manifest files

Every Zig project has two: build.zig.zon (the manifest) and build.zig (the build script).

build.zig.zon

ZON stands for "Zig Object Notation" — a subset of Zig used as a data format. The manifest declares metadata:

${z(`.{ .name = .hello, .version = "0.1.0", .fingerprint = 0x1234567890abcdef, .minimum_zig_version = "0.16.0", .dependencies = .{}, .paths = .{ "build.zig", "build.zig.zon", "src", "LICENSE", "README.md", }, }`)}

The fingerprint is generated by zig init and uniquely identifies the package. paths declares which files belong to the package — anything not listed won't be archived when others depend on you.

build.zig

This is the build script. zig build compiles it, runs the build function, and uses what that function declares to drive the build.

${z(`const std = @import("std"); pub fn build(b: *std.Build) void { const target = b.standardTargetOptions(.{}); const optimize = b.standardOptimizeOption(.{}); const exe_mod = b.createModule(.{ .root_source_file = b.path("src/main.zig"), .target = target, .optimize = optimize, }); const exe = b.addExecutable(.{ .name = "hello", .root_module = exe_mod, }); b.installArtifact(exe); const run_cmd = b.addRunArtifact(exe); if (b.args) |args| run_cmd.addArgs(args); const run_step = b.step("run", "Run the app"); run_step.dependOn(&run_cmd.step); const tests = b.addTest(.{ .root_module = exe_mod }); const run_tests = b.addRunArtifact(tests); const test_step = b.step("test", "Run unit tests"); test_step.dependOn(&run_tests.step); }`)}

The mental model

Three things to internalize:

  1. build.zig is itself a Zig program. It runs at build configure time and tells the build runner what to do.
  2. It builds a graph of steps. Each call like b.addExecutable, b.addRunArtifact, b.addTest creates a node. dependOn creates edges.
  3. Steps execute when something asks for them. b.installArtifact hooks the executable into the default install step. Custom steps like run and test are invoked by name on the command line.

Common commands

${sh(`$ zig build # default step: install $ zig build run # the custom 'run' step $ zig build test # the custom 'test' step $ zig build run -- arg1 arg2 # pass args to the program (b.args) $ zig build -Doptimize=ReleaseFast $ zig build -Dtarget=aarch64-linux-musl $ zig build --summary all # show every step that ran`)}

Project layout

There is no enforced layout. Convention is:

${sh(`hello/ ├── build.zig ├── build.zig.zon ├── src/ │ ├── main.zig │ └── lib/ │ └── parser.zig └── tests/ (optional, often tests live next to code)`)}

Two ways to organize code

Within Zig, code is organized into modules (in the build sense) and files (which are themselves struct literals at the language level). For small projects, the file-as-struct view is usually all you need; for libraries with dependencies, the module-as-build-unit view matters. Part X handles the latter.
