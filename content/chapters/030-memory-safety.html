Zig is not memory-safe in the way Rust is — there's no borrow checker, and the type system doesn't prevent every misuse of pointers. What Zig does have is a comprehensive runtime safety story in debug builds: most memory bugs panic with a clear message instead of corrupting your program silently. Combined with the GPA's leak detector, this catches a remarkable fraction of bugs in practice.

Build modes and safety

Zig has four build modes, each with a different tradeoff:

  • Debug — every safety check enabled, no optimization. Default for zig build.
  • ReleaseSafe — optimizations on, runtime safety checks kept.
  • ReleaseFast — optimizations on, safety checks off. UB on the slip.
  • ReleaseSmall — like ReleaseFast but tuned for binary size.

Most production code should default to ReleaseSafe. The performance gap to ReleaseFast is usually small; the safety gap is enormous.

What safety checks catch

In safe builds, the runtime catches:

  • Integer overflow on +, -, * (use +%/-%/*% to wrap).
  • Division by zero, integer remainder by zero.
  • Out-of-bounds slice/array indexing.
  • Out-of-bounds slice creation (arr[5..2], arr[0..arr.len+1]).
  • Reaching unreachable.
  • Cast that doesn't fit (@intCast losing bits, @enumFromInt with unknown value).
  • Dereferencing null in an unwrapped optional (optional.? on null).
  • Use-after-free of GPA allocations (in safe modes; GPA pads and quarantines).
  • Double-free of GPA allocations.
  • Many alignment violations on pointer casts.

Each violation panics with a return trace pointing at the failing operation. No silent corruption.

What safety checks miss

The checks are not exhaustive. Notably:

  • Dangling pointers to stack memory after the stack frame returns. Returning &local compiles and may not crash until much later.
  • Iterator invalidation: appending to a slice you're iterating over may relocate the backing buffer; the iterator is now garbage.
  • Data races between threads (Zig has atomics, but no race detector).
  • Aliasing of mutable references — possible to have two *Ts into the same memory.

None of these are common with disciplined Zig style — but they're not compiler-prevented. The borrow checker shaped hole has to be filled by the programmer.

undefined as a debug trap

Assigning undefined to a variable doesn't make it null or zero — in safe builds, it fills the memory with 0xAA bytes. Reading from it before writing produces obvious garbage, which is much louder than silent zero-init bugs.

GPA's special powers

The GeneralPurposeAllocator is much more than a heap. It:

  • Tracks every live allocation with a stack trace of its creation site.
  • Tracks every freed allocation with a stack trace of its free site.
  • Pads allocations and detects writes past the end.
  • Detects double-free and use-after-free against its records.
  • Reports any leaks at deinit() with stack traces of where the leaked memory was allocated.

Run your tests under GPA (or testing allocator, which is GPA) and most memory bugs become visible the moment they happen, with full context.

Defensive habits

Beyond what the compiler does for you:

  • Pair every alloc/create with a defer free/destroy on the next line.
  • Pair every init with a defer deinit.
  • Use errdefer when a partially constructed object needs to be torn down on failure.
  • Prefer slices to many-pointers; the length information catches off-by-one bugs.
  • Prefer optionals to "sentinel pointer" tricks; the type system catches missed null checks.
  • Keep functions short. Long functions with many allocations are where leaks hide.

These habits compound. A codebase that lives by them tends to be near-leak-free by construction, not by audit.
