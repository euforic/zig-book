Most Zig functions follow a small set of error patterns. Once they're in your fingers, error handling is unobtrusive — you barely notice it because it's always the right amount of code.

Propagate everything: try

The most common pattern is "do this; if it fails, fail the same way":

${z(`fn copy(io: std.Io, allocator: std.mem.Allocator, src: []const u8, dst: []const u8) !void { const cwd = std.Io.Dir.cwd(); const data = try cwd.readFileAlloc(io, src, allocator, .limited(1 << 20)); defer allocator.free(data); try cwd.writeFile(io, .{ .sub_path = dst, .data = data }); }`)}

Two operations, two trys, one inferred error set merging both. Nothing else needed.

Provide a default: catch <value>

When the failure isn't really a failure, just an absence:

${z(`const port = parsePort(env_value) catch 8080; const home = init.environ_map.get("HOME") orelse "/";`)}

The right-hand side of catch must have the same type as the success payload.

Handle specific errors: catch with switch

To branch on which error happened:

${z(`const f = std.Io.Dir.cwd().openFile(io, path, .{}) catch |err| switch (err) { error.FileNotFound => return defaults, error.AccessDenied => { std.log.warn("can't read {s}", .{path}); return error.Skipped; }, else => |e| return e, };`)}

The else => |e| return e arm rethrows anything you didn't handle. Without it, the switch must be exhaustive over the function's error set — which is sometimes what you want, sometimes too rigid.

Roll back on error: errdefer

You met defer already. errdefer is its asymmetric cousin: it runs only if the enclosing scope returns an error.

${z(`fn createUser(allocator: std.mem.Allocator, name: []const u8) !*User { const user = try allocator.create(User); errdefer allocator.destroy(user); user.name = try allocator.dupe(u8, name); errdefer allocator.free(user.name); try database.insert(user); return user; }`)}

If database.insert fails, both errdefers fire (last registered, first run): free the name, then destroy the user. On success, neither runs and the caller owns everything.

${tip("errdefer pairs with try", "

Whenever you allocate or acquire a resource and then call a fallible function, write the errdefer cleanup right under the acquisition. Read top to bottom: \"acquire / on-failure release / next step.\"

")}

Capture the error in errdefer

Modern Zig lets errdefer bind the error value, so cleanup can log or branch on what went wrong:

${z(`fn step() !void { var things: u32 = 0; errdefer |err| std.log.warn("step failed with {} after {} items", .{ err, things }); while (more()) : (things += 1) try processOne(); }`)}

Error return traces

When a Zig program returns an error from main, the runtime prints a return trace: every return error.X and every try on the path that propagated it. This is not a stack trace of where the program is; it's a trace of how the error got here.

${sh(`error: NotFound /home/zig/app.zig:12:5: in loadConfig const file = try std.Io.Dir.cwd().openFile(io, path, .{}); ^ /home/zig/app.zig:24:9: in main const cfg = try loadConfig(alloc, "config.toml"); ^`)}

Return traces have near-zero cost on the success path; they only allocate when an error is actually returned, and only in debug/safe build modes.

unreachable for "this error cannot happen"

If your domain knowledge tells you an error is impossible, you can assert it:

${z(`const data = readFromMemory(buf) catch unreachable;`)}

This is a strong claim — in safe builds, hitting unreachable panics; in ReleaseFast/ReleaseSmall it's undefined behavior. Use it sparingly, and prefer catch |e| std.debug.panic("bug: {}", .{e}) when you want the panic but not the UB.

A whole pattern in one function

${z(`fn buildIndex(allocator: std.mem.Allocator, paths: []const []const u8) !*Index { const idx = try allocator.create(Index); errdefer allocator.destroy(idx); idx.* = .{ .entries = .empty }; errdefer idx.entries.deinit(allocator); for (paths) |p| { const entry = parseEntry(p) catch |e| switch (e) { error.Empty => continue, else => return e, }; try idx.entries.append(allocator, entry); } return idx; }`)}

One try per fallible call, one errdefer per acquired resource, one explicit catch where the policy is "skip empties, fail on anything else." This is what idiomatic error code looks like.
