Zig is a small systems programming language whose stated ambition is to be a better C. Not a safer Rust, not a leaner Go — a better C: simple, transparent, and entirely under your control. Andrew Kelley began working on it in 2016, and the project has been refining a single idea ever since:

A programming language should reveal what your program is doing, not hide it.

This sounds like a slogan, but Zig takes it literally. There is no hidden control flow. There is no hidden memory allocation. There is no preprocessor and no macro system. There are no constructors, no destructors, no operator overloading, no exception handling, no garbage collector, no runtime that does work behind your back. When something happens in a Zig program, you wrote a line of code that made it happen.

What Zig gives you instead

Stripping all of that out would just leave you with a worse C, so Zig adds carefully chosen features in exchange:

  • Compile-time code execution. Any Zig function can run at compile time. Generic types are written as regular functions that take and return types. There's no separate template language; metaprogramming is programming.
  • Explicit allocators. Functions that allocate take an Allocator as a parameter. The standard library never allocates without one. You always know who owns the memory, and you can swap implementations trivially.
  • Errors as values. A function that can fail returns an error union (!T). The compiler refuses to let you ignore errors, but the syntax for handling them — try, catch, errdefer — stays out of the way.
  • Optionals instead of null pointers. If a value might be missing, its type is ?T. The compiler enforces unwrapping before use. The billion-dollar mistake doesn't compile.
  • Defer for cleanup. defer runs at scope exit; errdefer runs only on error. Together they replace destructors with something simpler and more honest.
  • A toolchain that includes C. The zig binary is also a C and C++ compiler with built-in cross-compilation to most targets. Even if you write no Zig, zig cc is a remarkable tool.

Hello, world

The traditional first program. We'll spend the next chapter installing the compiler and the chapter after that explaining every line, but here it is so you know what you're getting into.

${z(`const std = @import("std"); pub fn main() void { std.debug.print("Hello, Zig!\\n", .{}); }`)}

That's it. No header files. No preprocessor. No semicolon-juggling. The @import is a compile-time function that returns a module; std.debug.print is just a function call; .{} is an anonymous empty tuple of format arguments. Every glyph on the screen exists for a reason you'll understand by the end of Chapter 4.

Zig is small

The complete language reference fits in one HTML page. There are 22 keywords. There is one loop construct that handles both ranges and iterables (for) and one that handles conditions (while). There is no foreach, no do-while, no class declarations, no trait system, no lifetime annotations, no inheritance hierarchy.

This is the source of Zig's appeal. You can hold the whole language in your head. Once you do, the only thing left is the standard library and the problem you're trying to solve.

What you should know before continuing

You need to be comfortable with at least one programming language and understand the difference between a stack and a heap. You don't need to have written C, but you should be willing to think about memory: where it lives, who owns it, and when it goes away. Zig is not a language that lets you avoid those questions.

You should also have a terminal you're not afraid of. Most of what we do in this book involves running zig build from a shell and reading the compiler's error messages — which, by the way, are some of the best in any modern language.
