The language reference is complete, but it is intentionally dense. This chapter covers the reference topics beginners tend to miss because they are small, formal, or scattered across many sections.

Comments and documentation

Zig has line comments only. A normal comment starts with //. A doc comment starts with /// and documents the declaration immediately after it. A top-level doc comment starts with //! and documents the enclosing container, usually the file.

${z(`//! Module-level docs for this file. /// Adds two unsigned integers. pub fn add(a: u32, b: u32) u32 { // Ordinary implementation note. return a + b; }`)}

There are no block comments. This keeps the tokenizer simple and prevents accidentally commenting out half a file in a way that changes nested code.

Identifiers and string names

Normal identifiers use letters, digits, and underscores, and cannot be keywords. When you need a symbol that is not a normal identifier, use @"...". This is common for C symbols, exported names, tests, or interop with systems that use names Zig would not normally accept.

${z(`export fn @"add-one"(x: i32) i32 { return x + 1; } const @"type" = 42; // legal, but usually a bad idea in ordinary code`)} ${tip("Use escaped identifiers at boundaries", `

Inside normal Zig code, prefer ordinary names. Use @\"...\" when the outside world forces a spelling: C ABI symbols, generated code, protocol fields, or tests with human-readable names.

`)}

Operators and precedence

Zig has no operator overloading. If you see +, it is built-in arithmetic; it never calls user code. The reference's operator table matters because similar-looking operators often carry different safety promises.

  • +, -, * trap on integer overflow in safe modes.
  • +%, -%, *% wrap in twos-complement arithmetic.
  • +|, -|, *| saturate at the type's min or max.
  • and, or, orelse, and catch short-circuit.
  • ++ concatenates arrays at compile time; ** repeats arrays at compile time.

When an expression is hard to read, use parentheses. Zig rewards explicit code more than clever precedence games.

Destructuring

Tuples, arrays, and vectors can be destructured into declarations. Use _ to discard a position.

${z(`const point = .{ 10, 20 }; const x, const y = point; const rgb = [_]u8{ 255, 128, 0 }; const red, _, const blue = rgb;`)}

Destructuring is best for small, obvious groupings. If the values have names that matter, a struct is usually clearer.

Opaque types

opaque {} declares a distinct type whose size and layout are unknown to Zig code. You normally hold it through a pointer. It is the right tool for handle-based C APIs and type-erased boundaries where consumers must not inspect internals.

${z(`const sqlite3 = opaque {}; extern fn sqlite3_close(db: *sqlite3) c_int; pub fn closeDatabase(db: *sqlite3) void { _ = sqlite3_close(db); }`)}

void is a zero-bit type with known size. anyopaque is an unknown non-zero type used for type-erased pointers. They are not interchangeable.

Zero-bit types

Some types carry information in the type system while occupying no runtime storage. void, empty structs, and enums with one tag can all be zero-bit. This is useful for maps-as-sets, marker values, and generic code that sometimes needs no payload.

${z(`const Marker = struct {}; const Mode = enum { fast }; comptime { std.debug.assert(@sizeOf(void) == 0); std.debug.assert(@sizeOf(Marker) == 0); std.debug.assert(@sizeOf(Mode) == 0); }`)}

Type coercion, casts, and peers

Zig has safe coercions for conversions that cannot lose information: for example, a value of a smaller error set can coerce into a larger error set, and a string literal can coerce to []const u8. Everything else should be explicit with a builtin such as @as, @intCast, @floatFromInt, @ptrCast, or @alignCast.

Peer type resolution happens when multiple branches or operands must agree on one result type: if, switch, loop expressions, labeled blocks with multiple break values, and many binary operators.

${z(`const value: i64 = if (true) 10 else @as(i64, 20); const tag = switch (@as(u2, 1)) { 0 => "zero", 1 => "one", else => "many", };`)}

Result location semantics

Zig often knows where an expression's result is going before the expression is fully analyzed. That destination is the result location. It drives type inference and can avoid temporary copies.

${z(`const list: [3]u8 = .{ 1, 2, 3 }; // array literal gets its type from the destination fn choose(flag: bool) u8 { return if (flag) 1 else 2; // branches resolve to the function return type }`)}

This is why annotations near the outside of an expression can make the inside compile. When inference seems mysterious, ask: what type is the result being asked to become?

Compile variables and the compilation model

@import("builtin") exposes compile-time facts: target, optimization mode, output mode, link mode, and more. Use it for platform-specific code that must be decided at compile time.

${z(`const builtin = @import("builtin"); pub fn pathSeparator() u8 { return switch (builtin.target.os.tag) { .windows => '\\\\', else => '/', }; }`)}

Zig compiles a graph of modules. Files are containers, declarations are lazily analyzed, and comptime code runs during compilation. That is why unused broken declarations may not fail until something references them, while syntax errors always fail immediately.

Source encoding and style

Zig source is UTF-8. Invalid UTF-8 is a compile error. Identifiers should stay ASCII unless you have a strong reason, because code is read in terminals, diffs, debuggers, and generated documentation.

The official style is simple: types are TitleCase; functions, variables, fields, and declarations are snake_case; acronyms follow the same rule as other words. Prefer names that state ownership and side effects clearly.

Keyword map

You do not need to memorize every keyword at once. Group them by job:

  • Declarations: const, var, fn, test, pub, export, extern, threadlocal.
  • Types and layout: struct, enum, union, opaque, packed, align, addrspace, linksection, callconv.
  • Control flow: if, else, switch, while, for, break, continue, return.
  • Error and optional flow: try, catch, orelse, defer, errdefer, unreachable.
  • Compile-time and codegen: comptime, inline, noinline, asm.
  • Boolean logic: and, or.

Try it: reference drills

Add these to your notebook project as tests. They are intentionally small; the goal is to make the reference rules concrete.

${z(`const std = @import("std"); test "destructuring and peer type resolution" { const pair = .{ @as(u8, 1), @as(u16, 2) }; const a, const b = pair; const total: u16 = a + b; try std.testing.expectEqual(@as(u16, 3), total); } test "zero-bit marker" { const Seen = struct {}; try std.testing.expectEqual(@as(usize, 0), @sizeOf(Seen)); }`)}
