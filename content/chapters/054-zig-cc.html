When you install Zig, you also get a C compiler. zig cc is a clang-compatible front-end that uses Zig's bundled libc headers and cross-compilation infrastructure. zig c++ is the C++ counterpart. They accept all the clang flags you already know — -O2, -Wall, -I, -D, -c, -o — and add Zig's superpower: targeting any platform without installing a cross-toolchain.

Why this exists

The Zig compiler already needs LLVM to compile Zig. LLVM already includes clang. The bundled libc headers already exist to support Zig's interop story. Wiring up a clang front-end on top is mostly free. The result is a compiler that:

  • Cross-compiles C and C++ to any supported target out of the box.
  • Produces deterministic output — same input, same hash.
  • Acts as a drop-in for cc in most build systems.
  • Ships as a single tarball with no environment setup.

Using zig cc

${sh(`# Compile a C program for the host zig cc hello.c -o hello # Cross-compile to Linux ARM64 zig cc hello.c -target aarch64-linux-musl -o hello-arm # Cross-compile to Windows zig cc hello.c -target x86_64-windows-gnu -o hello.exe # Statically link against musl libc zig cc hello.c -target x86_64-linux-musl -o hello-static`)}

Notice that -target is the only flag that changes between hosts and architectures. Compare this with installing GCC cross-toolchains for each platform.

Using zig cc as your CC

Most build systems honor a CC environment variable. Setting CC="zig cc" usually works for Make, Autotools, CMake, and Meson:

${sh(`export CC="zig cc" export CXX="zig c++" export CC_FOR_TARGET="zig cc -target aarch64-linux-musl" ./configure --host=aarch64-linux-musl make`)}

Some build systems use idiosyncratic clang flags or check compiler identity by parsing version strings. The Zig wiki tracks known projects and workarounds.

Reproducible builds

System compilers vary: different distros, different glibc versions, different patch sets. zig cc is bit-identical on every host (modulo the Zig version). Combined with content-addressed dependencies, this makes Zig-driven builds reproducible in the strict sense: build the same source on three different machines, get three identical artifacts.

${tip('Use zig cc -### to see the exact arguments Zig is passing to clang. This is the fastest way to debug a build system that\\u2019s misbehaving with a custom CC.')}

Mixing zig cc with Zig code

Inside build.zig, you don't need to invoke zig cc manually — addCSourceFile already routes through the same machinery. Use zig cc when you're driving builds from outside Zig: shell scripts, Makefiles, integration with non-Zig ecosystems.

zig c++ for C++

zig c++ works the same way and ships with libc++ for the targets that need it. Templated C++ code, exceptions, RTTI, and the standard library all work. It's not a complete replacement for every C++ toolchain — projects that depend on Microsoft's MSVC ABI quirks or specific GCC ABI behavior may need patches — but for a large class of C++ code, it just works.

${sh(`zig c++ main.cpp -std=c++20 -O2 -o app zig c++ main.cpp -target aarch64-linux-musl -static -o app-arm`)}

Caveats

${warn('zig cc does not bundle every C library — only libc. If your code needs OpenSSL, zlib, libcurl, or another third-party library, you must build or vendor it yourself. The advantage is that you can cross-compile those libraries with zig cc too.')} ${note('macOS targets that need framework headers (Foundation, AppKit) require an Apple SDK because Apple does not distribute those headers under a free license. For pure ANSI C and POSIX, no SDK is needed.')}

Real-world use cases

  • Docker images. A single Zig install in your CI image cross-compiles for x86 and ARM Linux without QEMU.
  • Embedded firmware. Target Cortex-M with -target thumb-freestanding and a custom linker script.
  • Native modules for scripting languages. Compile a Python extension for Linux, macOS, and Windows from a Linux build host.
  • Reproducible release tarballs. Produce identical binaries on every developer machine.
