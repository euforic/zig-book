Functions in Zig are about as plain as functions can be. They take parameters by value, return a single value, and have no special "method" or "constructor" syntax. What makes them interesting is what their parameters can be — comptime values, types, and so on — and that they are first-class values you can pass around.

Declaration

${z(`fn add(a: i32, b: i32) i32 { return a + b; } pub fn greet(name: []const u8) void { std.debug.print("Hello, {s}!\\n", .{name}); }`)}

The keyword is fn. Parameters list types after their names. The return type comes after the closing paren. pub exports; without it the function is file-local.

Parameters are immutable

Function parameters are like const bindings: you can't reassign them inside the function body.

${z(`fn double(x: i32) i32 { // x = x * 2; // error return x * 2; }`)}

If you want a mutable local, copy it:

${z(`fn factorial(n: u32) u32 { var x = n; var result: u32 = 1; while (x > 1) : (x -= 1) result *= x; return result; }`)}

Pass by value, mostly

Small values (integers, small structs) are passed in registers. Large values are passed by hidden reference for efficiency, but you can't observe the difference: the parameter is conceptually a copy and the caller's value is unaffected.

If you need to mutate caller state, pass a pointer:

${z(`fn increment(p: *u32) void { p.* += 1; } var n: u32 = 5; increment(&n); // n is 6`)}

Multiple return values

Zig has no tuple syntax for multiple returns at the language level; you return a struct (named or anonymous):

${z(`fn divmod(a: u32, b: u32) struct { q: u32, r: u32 } { return .{ .q = a / b, .r = a % b }; } const result = divmod(17, 5); std.debug.print("{} {}\\n", .{ result.q, result.r }); // 3 2`)}

Functions as values

Functions are values of pointer type. You can put them in variables, pass them as parameters, store them in struct fields:

${z(`fn apply(f: *const fn (i32) i32, x: i32) i32 { return f(x); } fn square(x: i32) i32 { return x * x; } const y = apply(square, 5); // 25`)}

The type *const fn (i32) i32 reads "const pointer to a function taking i32 and returning i32." The *const part is mandatory; Zig has no bare function-value type the way C does. In practice you don't see it often because most function values flow through generic parameters or are used directly.

Anonymous functions are not a thing

Zig has no closures and no lambda syntax. If you need a small function-like construct, you can define a local fn as a static member of a struct literal, but it has no access to enclosing locals.

${z(`const helpers = struct { fn lessThan(a: u32, b: u32) bool { return a < b; } }; std.mem.sort(u32, &items, {}, helpers.lessThan);`)}

Variadic functions

Zig has no traditional varargs. The standard pattern is "a tuple of anytypes" passed as a single value:

${z(`fn printAll(args: anytype) void { inline for (args) |arg| { std.debug.print("{any} ", .{arg}); } } printAll(.{ 1, "hello", 3.14, true });`)}

The compiler expands the body for each call site, so this is zero-cost at runtime — and type-safe.

Comptime parameters

A parameter declared comptime must be known at compile time. This is how generics are written:

${z(`fn max(comptime T: type, a: T, b: T) T { return if (a > b) a else b; } const m = max(i32, 3, 7); // 7 const mf = max(f64, 1.0, 2.5); // 2.5`)}

Each instantiation produces specialized code. We dive deep into this in Part VII.

inline and noinline

Functions can be marked inline or noinline to advise the compiler. inline fn also affects semantics: calls become inline calls, comptime context can flow through, and the function can't be taken as a value.

${z(`inline fn square(x: i32) i32 { return x * x; }`)}

Use sparingly. The compiler is good at inlining on its own.

Return types you'll meet often

  • void — no return value (implicit at end).
  • T — a normal value.
  • !T — error union, see Part V.
  • ?T — optional, see Chapter 20.
  • noreturn — never returns, see Chapter 8.

extern, export, and callconv

Three attributes you'll need when interoperating with C:

  • extern fn — declared in Zig, defined elsewhere (linked from a C library).
  • export fn — defined in Zig, made visible with C linkage so others can link it.
  • callconv(.c) — use the C calling convention instead of Zig's. Required for extern/export entry points.
${z(`pub extern "c" fn malloc(n: usize) ?*anyopaque; pub export fn add_ints(a: c_int, b: c_int) callconv(.c) c_int { return a + b; }`)}

We'll come back to this in Part XI.
