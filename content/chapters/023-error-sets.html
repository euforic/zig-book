Zig has no exceptions. A function that can fail returns an error union, and errors themselves are values drawn from error sets — enum-like collections of error names. The type system tracks exactly which errors a function can produce, and the compiler will complain if you forget to handle one.

This sounds heavy. In practice it's lightweight: most of the time you write !T, let inference figure out the error set, and use try to propagate. The full mechanism is there when you need it.

Declaring an error set

An error set is a type. Declare one with error { ... }:

${z(`const FileError = error{ NotFound, PermissionDenied, DiskFull, }; fn open(path: []const u8) FileError!File { _ = path; return error.NotFound; }`)}

Inside a function, error.NotFound creates a value of that error. The set type written before the ! says which errors the function can return.

The global error set

Every error name you mention anywhere in your program participates in a single, program-wide implicit set. The type anyerror represents that whole set — any error from anywhere:

${z(`fn anything() anyerror!void { return error.SomethingBroke; }`)}

anyerror is convenient but lossy: callers no longer know exactly what can fail. Reserve it for very generic interfaces. Most functions should have a precise set, or simply let it be inferred.

${note("anyerror is a fallback", "

Treat anyerror like any in TypeScript or Box<dyn Error> in Rust: useful as glue, harmful as default. Precise sets are documentation the compiler enforces.

")}

Inferred error sets

Write !T without naming a set, and Zig infers the set from the function body:

${z(`fn parse(s: []const u8) !i32 { if (s.len == 0) return error.Empty; if (s[0] == '-') return error.Negative; return @intCast(s[0] - '0'); }`)}

The inferred set is exactly error{Empty,Negative} plus whatever the body's try expressions can return. This is the most common form — explicit sets are for public APIs where you want stability.

Set algebra

Error sets compose. The || operator merges sets:

${z(`const ParseError = error{ Empty, BadDigit }; const IoError = error{ NotFound, PermissionDenied }; const AllError = ParseError || IoError; // AllError == error{ Empty, BadDigit, NotFound, PermissionDenied }`)}

If an error name appears in both, it appears once in the union. There's also a subset check: SmallSet coerces to BigSet automatically when every variant fits.

switch on errors

You can switch on an error value as if it were an enum:

${z(`fn classify(err: FileError) []const u8 { return switch (err) { error.NotFound => "missing", error.PermissionDenied => "forbidden", error.DiskFull => "out of space", }; }`)}

The switch must be exhaustive over the set — leave a case off and the compiler will tell you.

Error sets are types, not enums

Error names are global to the program: every error.NotFound refers to the same value, regardless of which set declared it. Sets are just type-level filters that say which subset of names a function admits.

${z(`const A = error{ X }; const B = error{ X }; // A.X == B.X — same value, two filters over it.`)}

This means error names are cheap and you should not feel bad about reusing common ones (OutOfMemory, InvalidInput, EndOfStream) across modules. The standard library does exactly this.
