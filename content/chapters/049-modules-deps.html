Zig has a built-in package manager. Dependencies are declared in build.zig.zon (Zig Object Notation, a JSON-like syntax that's actually Zig comptime values). Fetching happens automatically when you run zig build; sources are stored in a global cache keyed by content hash; integrity is enforced via SHA-256.

The .zon file

${code('zig', `.{ .name = .my_project, .version = "0.1.0", .fingerprint = 0xabc123def456789a, .minimum_zig_version = "0.16.0", .dependencies = .{ .mach = .{ .url = "https://github.com/hexops/mach/archive/.tar.gz", .hash = "1220abcd...ef01", }, .local_helpers = .{ .path = "deps/helpers", }, }, .paths = .{ "build.zig", "build.zig.zon", "src", "LICENSE", "README.md", }, }`)}

Each dependency entry is either a URL with an expected content hash (Zig refuses to use a tarball whose hash doesn't match) or a local .path for in-tree packages. The .paths field declares which files belong to this package when it is consumed as a dependency — this lets you exclude test data, benchmarks, or examples from downstream tarballs.

${note('0.16 fingerprints. Every package gets a unique fingerprint generated at zig init time. It identifies the package across renames and helps the build system detect when two dependencies are actually the same upstream project under different names.')}

Adding a dependency to your build

${z(`const mach = b.dependency("mach", .{ .target = target, .optimize = optimize, }); const root = b.createModule(.{ .root_source_file = b.path("src/main.zig"), .target = target, .optimize = optimize, }); root.addImport("mach", mach.module("mach"));`)}

b.dependency resolves the dependency at build time, passing through option values. dep.module("name") retrieves a module the dependency author exported in their own build.zig. Now your code can @import("mach").

Fetching

Run zig fetch --save URL to download a tarball, compute its hash, and update build.zig.zon automatically. This is the recommended way to add a dependency — it removes the manual "copy the hash from the error message" step.

${sh(`# Add a dependency by URL zig fetch --save https://github.com/example/lib/archive/v1.2.3.tar.gz # Use a git ref zig fetch --save git+https://github.com/example/lib#main`)}

Local package overrides

When you are debugging a bug across your app and a library, you can point a dependency at a local checkout without editing build.zig.zon.

${sh('zig build --dep-overrides=mach=../mach-fork')}

This swaps the resolved location of mach without modifying build.zig.zon. CI continues using the upstream pin; you iterate locally.

Project-local fetch directory

By default, fetched packages land in the global cache at ~/.cache/zig. You can opt into a project-local directory:

${sh('zig build --global-cache-dir .zig-cache/global')}

Useful for sandboxed CI environments, reproducible builds, or when you simply don't want cross-project cache pollution.

Exposing modules from your package

If you're publishing a library, downstream consumers will call dep.module("yourname"). You have to declare which modules to expose:

${z(`const lib_mod = b.addModule("mylib", .{ .root_source_file = b.path("src/root.zig"), .target = target, .optimize = optimize, }); const lib = b.addLibrary(.{ .linkage = .static, .name = "mylib", .root_module = lib_mod, }); b.installArtifact(lib);`)}

addModule (vs createModule) registers the module by name on the build graph, making it discoverable to dependents. Publish your tag, point users at the URL, and they're consuming your library.

Try it: split an app into a package

Take any function from src/main.zig, move it to src/root.zig, and expose it as a named module. Then import that module back into the executable.

${z(`const lib_mod = b.addModule("tool_core", .{ .root_source_file = b.path("src/root.zig"), .target = target, .optimize = optimize, }); const exe_mod = b.createModule(.{ .root_source_file = b.path("src/main.zig"), .target = target, .optimize = optimize, }); exe_mod.addImport("tool_core", lib_mod);`)}

Now src/main.zig can call @import("tool_core"). This is the smallest version of the package boundary you will use in real projects.

${warn('Hashes are non-negotiable. If a tarball at a URL changes content but keeps the same URL, the hash mismatch will fail the build. This is intentional — supply-chain integrity is enforced, not advisory.')}
