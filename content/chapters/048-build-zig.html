Most language build systems are configuration files: Makefile, CMakeLists.txt, Cargo.toml, package.json. They have their own grammar, their own conditional syntax, their own template languages. Zig made a different choice. A Zig project's build description is a Zig program named build.zig that exports a build function. The zig build command compiles that program and runs it.

The consequence is that everything you've learned applies. Conditionals are if. Loops are for. Functions are functions. Cross-platform logic is regular comptime branching. There is no DSL to learn — there's just an API.

The minimal build.zig

${z(`const std = @import("std"); pub fn build(b: *std.Build) void { const target = b.standardTargetOptions(.{}); const optimize = b.standardOptimizeOption(.{}); const exe = b.addExecutable(.{ .name = "hello", .root_module = b.createModule(.{ .root_source_file = b.path("src/main.zig"), .target = target, .optimize = optimize, }), }); b.installArtifact(exe); const run_cmd = b.addRunArtifact(exe); run_cmd.step.dependOn(b.getInstallStep()); if (b.args) |args| run_cmd.addArgs(args); const run_step = b.step("run", "Run the app"); run_step.dependOn(&run_cmd.step); }`)}

Read this top to bottom. standardTargetOptions wires up -Dtarget=... so users can cross-compile. standardOptimizeOption wires up -Doptimize=Debug|ReleaseSafe|ReleaseFast|ReleaseSmall. addExecutable declares an output. installArtifact says "when the user runs zig build install (the default step), copy this artifact to zig-out/bin/." step declares a named user-facing command.

The graph metaphor

What you're really doing is building a directed acyclic graph of steps. Each step has dependencies. When you run zig build run, the system topologically sorts and executes only what's needed. Steps are nodes; dependOn adds edges. The build system parallelizes execution where the graph allows.

Module objects

A module is a unit of Zig source code with its own root file, target, optimization mode, and dependencies. Executables, static libraries, dynamic libraries, and tests all wrap modules. Modules can depend on other modules — that's how you compose code across files and packages.

${z(`const utils = b.createModule(.{ .root_source_file = b.path("src/utils.zig"), .target = target, .optimize = optimize, }); const root = b.createModule(.{ .root_source_file = b.path("src/main.zig"), .target = target, .optimize = optimize, }); root.addImport("utils", utils); const exe = b.addExecutable(.{ .name = "app", .root_module = root });`)}

Inside main.zig, you now write const utils = @import("utils");. Imports are named, not path-based.

User-defined options

${z(`const enable_telemetry = b.option(bool, "telemetry", "enable telemetry") orelse false; const max_threads = b.option(u32, "threads", "max worker threads") orelse 4; const options = b.addOptions(); options.addOption(bool, "enable_telemetry", enable_telemetry); options.addOption(u32, "max_threads", max_threads); root.addOptions("build_options", options);`)}

In code: const opts = @import("build_options"); if (opts.enable_telemetry) .... Options become a generated module whose contents are compile-time constants. This is how feature flags work without a preprocessor.

Libraries and linkage

Executables are only one artifact kind. The same module can back a static library, dynamic library, object file, or test artifact.

${z(`const lib_mod = b.createModule(.{ .root_source_file = b.path("src/root.zig"), .target = target, .optimize = optimize, }); const static_lib = b.addLibrary(.{ .linkage = .static, .name = "mylib", .root_module = lib_mod, }); b.installArtifact(static_lib); const shared_lib = b.addLibrary(.{ .linkage = .dynamic, .name = "mylib", .root_module = lib_mod, });`)}

Use static libraries for simple distribution and embedding. Use dynamic libraries when another runtime needs to load your code at runtime or when platform packaging expects shared objects.

C sources and system libraries

A Zig module can compile C files and link against system libraries. Keep this inside build.zig so cross-compilation settings flow through one graph.

Standard steps

By convention, projects expose a few named steps that users come to expect:

  • zig build — the default; usually equivalent to install.
  • zig build run — build and run the main executable.
  • zig build test — run unit tests.
  • zig build check — type-check without producing artifacts (fast for editor integration).
  • zig build docs — generate documentation HTML.

None of these are magic. They're just b.step(...) declarations in your build.zig. Run zig build --help to see what a given project supports.

Useful 0.16 flags

Several flags meaningfully improve daily use:

  • --error-style=... — choose how errors are printed (compact, verbose).
  • --multiline-errors — let error messages span multiple lines for readability.
  • --time-report — show a breakdown of where build time was spent.
  • --prominent-compile-errors — surface compile errors above test failures.
