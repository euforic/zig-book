Zig 0.16's headline change is I/O as an interface. std.Io is now the standard-library boundary for filesystem work, processes, networking, clocks, randomness, sleeping, structured concurrency, and synchronization primitives. Code that does those things should accept an io: std.Io parameter, just like allocation-heavy code accepts an allocator: std.mem.Allocator.

The practical result: libraries no longer hard-code "blocking syscall", "thread pool", or "event loop". The caller supplies the I/O implementation. Your function says what it needs to do; the application decides how operations are scheduled.

Juicy main

The usual 0.16 entry point accepts std.process.Init. It gives you a default allocator, process-lifetime arena, command-line arguments, environment variables, preopened files, and an appropriate std.Io implementation:

${z(`const std = @import("std"); pub fn main(init: std.process.Init) !void { const io = init.io; try std.Io.File.stdout().writeStreamingAll(io, "Hello from std.Io\\n"); const args = try init.minimal.args.toSlice(init.arena.allocator()); for (args, 0..) |arg, i| { std.log.info("arg[{d}] = {s}", .{ i, arg }); } }`)} ${note("Empty main still exists", "

pub fn main() !void is still legal, but it intentionally gives you no access to argv, env vars, the default process arena, or the process-selected std.Io. For real programs, prefer std.process.Init.

")}

Reader and Writer

std.Io.Reader and std.Io.Writer are buffered interface values. Their methods operate on the interface itself; the io handle lives in concrete producers like files, sockets, directories, and process APIs.

${z(`fn copyAll(src: *std.Io.Reader, dst: *std.Io.Writer) !void { _ = try src.streamRemaining(dst); try dst.flush(); } fn formatIntoBuffer() ![]const u8 { var buffer: [128]u8 = undefined; var writer = std.Io.Writer.fixed(&buffer); try writer.print("{s}: {d}\\n", .{ "count", 42 }); return writer.buffered(); }`)}

Writers buffer aggressively. If the destination is a file, socket, terminal, or pipe, call flush() before assuming bytes reached the outside world. Allocating writers are the exception: they grow memory and do not need flushing.

Fixed memory sources and sinks

${z(`var reader = std.Io.Reader.fixed("name=zig\\n"); const key = try reader.takeDelimiterExclusive('='); const value = try reader.takeDelimiterExclusive('\\n'); var out_buf: [64]u8 = undefined; var out = std.Io.Writer.fixed(&out_buf); try out.print("{s} -> {s}", .{ key, value }); const written = out.buffered();`)}

Files produce file readers and writers

${z(`pub fn readAndEcho(init: std.process.Init) !void { const io = init.io; const cwd = std.Io.Dir.cwd(); const file = try cwd.openFile(io, "data.txt", .{}); defer file.close(io); var read_buf: [4096]u8 = undefined; var file_reader = file.reader(io, &read_buf); var write_buf: [4096]u8 = undefined; var stdout = std.Io.File.stdout().writerStreaming(io, &write_buf); defer stdout.interface.flush() catch {}; _ = try file_reader.interface.streamRemaining(&stdout.interface); }`)}

Notice the layering: std.Io.File owns the OS handle; file.reader(io, buffer) creates a concrete file reader; file_reader.interface is the generic *std.Io.Reader you pass into parsing and streaming code.

Future and Group

std.Io.async returns a Future(T). std.Io.Group owns multiple Cancelable!void tasks and waits for them as a unit. Use these when you need structured concurrent I/O work.

${z(`fn fetchAll(io: std.Io, urls: []const []const u8) !void { var group: std.Io.Group = .init; errdefer group.cancel(io); for (urls) |url| { group.async(io, fetchOne, .{ io, url }); } try group.await(io); } fn fetchOne(io: std.Io, url: []const u8) std.Io.Cancelable!void { _ = io; _ = url; // network work goes here }`)}

Calling await or cancel releases the group's resources. If a function can fail after spawning work, use errdefer group.cancel(io) so spawned tasks do not outlive the scope accidentally.

Cancellation, sleep, time, and entropy

Cancellation is integrated into I/O operations. Sleep, filesystem calls, process waits, network operations, and many synchronization operations can return error.Canceled. Randomness also moved to std.Io:

${z(`try std.Io.sleep(io, .fromMilliseconds(250), .awake); var bytes: [32]u8 = undefined; io.random(&bytes); // may use process-local RNG state try io.randomSecure(&bytes); // always asks outside the process`)}

Implementations

The standard library exposes concrete implementations such as std.Io.Threaded and platform evented backends via std.Io.Evented. Most applications should start with the io provided by std.process.Init. Reach for an explicit implementation when you are writing a runtime, benchmark harness, server framework, or test environment that must control scheduling policy.

Everyday shape

  • Accept io: std.Io in code that touches the OS, waits, sleeps, spawns processes, or requests entropy.
  • Use std.Io.Dir and std.Io.File for filesystem handles.
  • Pass io to methods that may perform I/O: file.close(io), dir.openFile(io, ...), child.wait(io).
  • Use std.Io.async, std.Io.Future, and std.Io.Group for structured concurrent I/O work.
  • Use std.process.Init for real program entry points and io.random / io.randomSecure for randomness.
