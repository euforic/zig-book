One of Zig's most distinctive properties is that cross-compilation is built in by default. There is no separate cross-toolchain to install. The compiler ships with libc headers for major systems and uses lld for linking; from a single Zig install you can target Linux, macOS, Windows, FreeBSD, WebAssembly, multiple Arm variants, RISC-V, and more.

Specifying a target

${sh(`# Linux arm64 musl static binary, from any host zig build -Dtarget=aarch64-linux-musl -Doptimize=ReleaseFast # Windows x86_64 (gnu ABI) zig build -Dtarget=x86_64-windows-gnu # macOS arm64 zig build -Dtarget=aarch64-macos # WebAssembly with WASI zig build -Dtarget=wasm32-wasi`)}

Target triples follow the pattern arch-os-abi. The arch is the CPU family (x86_64, aarch64, riscv64, wasm32, etc.). The os is the operating system (linux, macos, windows, freebsd, wasi, freestanding). The abi is the binary interface (gnu, musl, msvc, none).

Targeting a specific CPU

You can refine the target with a CPU model or feature set:

${sh(`# Apple M1 specifically zig build -Dtarget=aarch64-macos -Dcpu=apple_m1 # x86_64 baseline + AVX2 + BMI2 zig build -Dtarget=x86_64-linux -Dcpu=baseline+avx2+bmi2 # Generic x86_64 with no SIMD assumptions zig build -Dtarget=x86_64-linux -Dcpu=x86_64`)}

The Zig tier system

Not every target gets the same level of support. The Zig project publishes a tier list in the release notes and platform-support documentation:

  • Tier 1 — fully supported, all tests pass, frequently used. Examples: x86_64-linux, aarch64-macos, x86_64-windows-msvc, wasm32-wasi.
  • Tier 2 — standard library mostly works; tests run; minor bugs possible. Examples: aarch64-linux, riscv64-linux, x86_64-freebsd.
  • Tier 3 — compiles but std incomplete; expect rough edges. Examples: many embedded targets, exotic OSes.
  • Tier 4 — experimental; expect to fix things yourself.

For production, prefer Tier 1 or 2. For Tier 3, plan extra QA time.

Building for many targets at once

${z(`pub fn build(b: *std.Build) void { const optimize = b.standardOptimizeOption(.{}); const targets: []const std.Target.Query = &.{ .{ .cpu_arch = .x86_64, .os_tag = .linux, .abi = .musl }, .{ .cpu_arch = .aarch64, .os_tag = .linux, .abi = .musl }, .{ .cpu_arch = .x86_64, .os_tag = .windows, .abi = .gnu }, .{ .cpu_arch = .aarch64, .os_tag = .macos }, }; for (targets) |query| { const resolved = b.resolveTargetQuery(query); const exe = b.addExecutable(.{ .name = "app", .root_module = b.createModule(.{ .root_source_file = b.path("src/main.zig"), .target = resolved, .optimize = optimize, }), }); const install = b.addInstallArtifact(exe, .{ .dest_dir = .{ .override = .{ .custom = try std.fmt.allocPrint( b.allocator, "{s}-{s}", .{ @tagName(query.cpu_arch.?), @tagName(query.os_tag.?) } ) } }, }); b.getInstallStep().dependOn(&install.step); } }`)}

A single zig build now produces four binaries in distinctly named subdirectories of zig-out. This pattern is how many projects publish release tarballs.

Cross-compiling C code

Zig bundles libc headers for major systems. When your project links against C code, those headers are picked up automatically for the chosen target. You don't install cross-toolchains; Zig is the cross-toolchain.

${tip('To see what triple your current build is using, run zig env. The target field shows the fully resolved target including CPU features.')}

Static vs dynamic linking

On Linux, the musl ABI produces statically-linked binaries with no external libc dependency. This is ideal for distribution: one binary runs on any Linux glibc version. The gnu ABI links dynamically against glibc, which is faster for some workloads but requires the target system to have a compatible glibc version.

${warn('macOS targets require Apple SDK headers for certain features (CoreFoundation, IOKit, etc.). For pure ANSI C and Zig std, no extra SDK is needed; for system framework access, you may need to provide an SDK path.')}

Try it: release one tiny binary

Pick the hello-world project and build it for your host plus one other target. Record the exact target triple and optimization mode in a RELEASE_NOTES.md scratch file.

${sh(`zig build -Doptimize=ReleaseSmall zig build -Dtarget=x86_64-linux-musl -Doptimize=ReleaseSmall find zig-out -type f -perm -111 -maxdepth 4`)}

The exercise is not the binary; it is noticing which parts of your program were host assumptions and which parts were portable Zig.
