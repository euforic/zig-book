The standard library ships about a dozen allocator implementations. You'll use four of them constantly and the rest occasionally. Here's the field guide.

GeneralPurposeAllocator (GPA)

The default for application code. Tracks every allocation, catches leaks and double-frees, validates pointers on free. Modestly slower than malloc but enormously safer.

${z(`var gpa: std.heap.GeneralPurposeAllocator(.{}) = .init; defer if (gpa.deinit() == .leak) @panic("memory leak"); const allocator = gpa.allocator();`)}

The deinit() call returns .leak if any allocations were never freed; it prints stack traces of each leaked allocation to help you find them. In release builds, you can configure GPA to skip the safety checks for performance.

ArenaAllocator

An arena allocates by bumping a pointer and frees everything at once. Per-allocation free is a no-op. Perfect for phases of work that have a clear endpoint: per-request, per-frame, per-parse.

${z(`var arena = std.heap.ArenaAllocator.init(parent_allocator); defer arena.deinit(); // frees EVERYTHING at once const allocator = arena.allocator(); const a = try allocator.alloc(u8, 100); const b = try allocator.alloc(u8, 200); // no free calls needed — arena.deinit() handles both _ = a; _ = b;`)} ${note("ArenaAllocator is thread-safe", "

ArenaAllocator uses a lock-free design that can be shared safely across threads. It is still best for batch lifetimes: allocate many related objects, then free them all at once with arena.deinit().

")}

FixedBufferAllocator

Allocates out of a fixed-size buffer you provide. When the buffer is full, allocations fail. Zero heap involvement. Excellent for embedded, hot paths, or testing OOM behavior.

${z(`var buf: [4096]u8 = undefined; var fba = std.heap.FixedBufferAllocator.init(&buf); const allocator = fba.allocator(); const data = try allocator.alloc(u8, 100); _ = data; // fba.reset() to recycle the whole buffer`)}

page_allocator

Allocates whole pages from the OS (mmap on Unix, VirtualAlloc on Windows). Very high per-allocation overhead (a page is typically 4 KiB minimum), but no bookkeeping. Useful as a backing allocator for arenas, or for huge buffers.

${z(`const allocator = std.heap.page_allocator; const huge = try allocator.alloc(u8, 1 << 24); // 16 MiB defer allocator.free(huge);`)}

c_allocator

Forwards to libc malloc/free. Available when you link libc. Useful for FFI scenarios where C code holds onto memory and frees it itself.

${z(`// build.zig: exe.linkLibC(); const allocator = std.heap.c_allocator; const buf = try allocator.alloc(u8, 1024); defer allocator.free(buf);`)}

std.testing.allocator

The allocator your test blocks should use. It's a GPA tuned for tests: it fails the test if any allocation isn't freed by the end of the test.

${z(`test "no leak" { const list = try std.testing.allocator.alloc(u32, 8); defer std.testing.allocator.free(list); list[0] = 42; try std.testing.expectEqual(@as(u32, 42), list[0]); }`)}

Forget the defer and the test fails with a clear leak report. This single mechanism catches a huge fraction of memory bugs before they leave your laptop.

StackFallbackAllocator

Tries to allocate from a stack buffer first; falls back to a parent allocator if the buffer is exhausted. Great for "usually small, sometimes huge" patterns:

${z(`var sfa = std.heap.stackFallback(256, gpa.allocator()); const allocator = sfa.get(); const buf = try allocator.alloc(u8, requested_size); defer allocator.free(buf);`)}

Small requests stay on the stack — no heap traffic. Large requests escape to the heap automatically.

Picking an allocator: a rough flowchart

  • Bounded size, short scope → stack buffer, no allocator.
  • One phase of work, free all at end → ArenaAllocator wrapping a GPA.
  • Long-lived data with mixed lifetimes → GeneralPurposeAllocator.
  • Hot path with predictable max size → FixedBufferAllocator or StackFallbackAllocator.
  • Inside a test → std.testing.allocator.
  • Talking to C → c_allocator.

Composition

Allocators compose. An arena on top of a GPA inherits the GPA's safety checks for the underlying pages while giving the arena's batch-free convenience for user code. A stack-fallback on top of an arena gives a per-frame allocator that mostly never touches the heap. Mix and match.
