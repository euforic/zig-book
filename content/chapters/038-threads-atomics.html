Zig's concurrency story is split between raw CPU concurrency and I/O-aware concurrency. Use std.Thread and atomics when you are directly managing threads or lock-free state. Use std.Io when operations may block, suspend, sleep, wait, or be canceled.

You still have raw threads and atomics for the cases Io doesn't cover. Blocking synchronization primitives that may wait now live under std.Io so they can participate in cancellation and the selected scheduler.

std.Thread

For one-shot threads or hand-rolled concurrency, std.Thread.spawn is the primitive:

${z(`const std = @import("std"); fn worker(id: usize) void { std.debug.print("hi from {}\\n", .{id}); } pub fn main() !void { var threads: [4]std.Thread = undefined; for (&threads, 0..) |*t, i| t.* = try std.Thread.spawn(.{}, worker, .{i}); for (threads) |t| t.join(); }`)}

spawn takes a function and a tuple of arguments. The function's signature determines the argument types; the compiler enforces matching. join waits for the thread to finish.

Mutex and condition variables

The waiting primitives live in std.Io:

${z(`var mutex: std.Io.Mutex = .init; var queue: std.ArrayList(Job) = .empty; fn submit(io: std.Io, allocator: std.mem.Allocator, job: Job) !void { try mutex.lock(io); defer mutex.unlock(io); try queue.append(allocator, job); }`)}

RwLock, Condition, Semaphore, Event, and Futex follow the same rule: pass io to operations that may wait or wake waiters.

Atomics

For lock-free programming, the atomic builtins (covered last chapter) give you the C++11 memory model. The std.atomic namespace adds a friendly typed wrapper:

${z(`var counter: std.atomic.Value(u32) = .{ .raw = 0 }; fn incr() void { _ = counter.fetchAdd(1, .monotonic); } fn read() u32 { return counter.load(.acquire); }`)}

The .Value type bundles the storage with its operations and avoids accidental non-atomic accesses.

Lazy init

Prefer passing initialized dependencies explicitly. If you truly need process-wide lazy initialization, build a small state machine with atomics and a mutex so ownership, failure behavior, and teardown are visible in your code.

Atomic memory orderings, the short version

If you're not sure which ordering to pick:

  • .seq_cst — safest, slowest. Default if you don't know.
  • .acquire on the load that publishes data; .release on the store. Standard ownership-transfer pattern.
  • .monotonic for counters where the order doesn't matter, only the count.
  • .unordered almost never — only for telemetry where lost updates are fine.

Get this wrong and your program will run fine on x86 (which has strong defaults) and break on ARM. Test on both if it matters.

Send-receive channels

Zig does not ship a built-in MPSC/MPMC channel in std. Build one on top of a mutex and a condition variable if you need it, or use a community library. The Io primitives also expose a futures-and-cancellation model that covers many coordination use cases — see Part IX.

I/O-aware concurrency

The answer to "how do I do async work?" is "use std.Io." The Io interface lets a function express "this is a fallible operation that may suspend" without a separate language keyword; an implementation can run those operations cooperatively on one thread, across worker threads, or against a kernel event loop, transparently to the caller.

If you're coming from an async-await background, the mental shift is: instead of awaiting individual operations, you write straight-line code against an Io handle, and the runtime decides where to suspend. Cancellation, batching, and structured concurrency are all first-class in the new interface.
