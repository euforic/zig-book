Small examples teach syntax. Projects teach judgment. This chapter gives you a set of deliberately scoped projects that exercise the parts of Zig you need in real work: command-line arguments, files, allocation, errors, tests, packages, interop, targets, and release builds.

How to work through a project

  1. Start with zig init and keep the generated build layout.
  2. Write one thin vertical slice before designing abstractions.
  3. Add tests as soon as a function has parsing, allocation, or error behavior.
  4. Expose zig build run, zig build test, and zig build check.
  5. Cross-compile once the local build is green.

`)}

Project 1: CLI file tool

Build a command named zcount that reads a file and reports bytes, lines, and UTF-8 codepoints. This forces you to use args, file I/O, slices, errors, and tests.

  • Core: zcount path/to/file prints counts.
  • Errors: missing argument, unreadable file, invalid UTF-8 if codepoint counting is requested.
  • Tests: count empty input, one-line input, trailing newline, and non-ASCII UTF-8.
  • Stretch: add --json output using std.json.
${z(`const Counts = struct { bytes: usize, lines: usize, }; pub fn countBytesAndLines(input: []const u8) Counts { var lines: usize = 0; for (input) |byte| { if (byte == '\\n') lines += 1; } return .{ .bytes = input.len, .lines = lines }; }`)}

Project 2: Config parser

Build a small app config loader. Parse JSON for compatibility and ZON for Zig-native configuration. The point is not a fancy app; the point is handling owned memory and typed data correctly.

  • Core: load name, port, and features into a typed struct.
  • Memory: decide whether parsed strings are borrowed from input or owned by an arena.
  • Errors: distinguish invalid syntax from missing required fields.
  • Tests: parse valid config, reject invalid port, handle missing optional fields.
${z(`const Config = struct { name: []const u8, port: u16 = 8080, features: []const []const u8 = &.{}, };`)}

Project 3: Reusable package

Extract a useful library from one of the first two projects. Publish it as a local package consumed by a separate example executable.

  • Package: expose a named module from build.zig.
  • Build options: add one -D option that changes behavior at compile time.
  • Tests: make zig build test run library tests.
  • Docs: add doc comments to the public API and run a docs build step if your project exposes one.

Project 4: C boundary or WebAssembly boundary

Pick one boundary depending on your interests.

  • C path: call a tiny C function from Zig, then export a Zig function callable from C.
  • WASM path: compile a freestanding Zig function to wasm32-freestanding and call it from a small host program.
  • Acceptance: reduce the boundary to integers, pointers, lengths, and explicit error codes. Do not pass Zig slices or error unions over a C ABI.

Project 5: Release matrix

Take any earlier project and make it shippable.

  • Build x86_64-linux-musl, aarch64-linux-musl, aarch64-macos, and x86_64-windows-gnu where your host can support them.
  • Add a dist or release build step that places artifacts in target-named directories.
  • Run the local artifact and at least one cross-compiled artifact under the appropriate runtime or VM if available.
  • Record exact Zig version and target triples in the release notes.

Completion checklist

You are ready to use Zig actively in projects when you can do these without copying a template blindly:

  • Explain who owns every allocated buffer in your program.
  • Read an unfamiliar build.zig and find its public steps.
  • Use std.testing.allocator or an arena deliberately in tests.
  • Turn a compiler error into a smaller repro.
  • Find the relevant stdlib implementation with rg.
  • Cross-compile a release build and know which target assumptions changed.
