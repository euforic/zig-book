Switch statements are usually fine. But when you're writing an interpreter, a state machine, or a tokenizer that loops on a switch every iteration, the compiler often can't see that "after handling this instruction, jump back to the top and switch on the next" is the actual hot path. Labeled switch — which Zig grew in 0.13 and which is now mature — lets you express direct jumps between switch arms, giving you a manual computed-goto without leaving safe Zig.

The basic syntax

You label a switch with label: and then jump to it from inside an arm with continue :label expr:

${z(`fn interpret(bytecode: []const u8) void { var pc: usize = 0; sw: switch (bytecode[pc]) { OP_ADD => { // ... do add ... pc += 1; continue :sw bytecode[pc]; }, OP_SUB => { // ... do sub ... pc += 1; continue :sw bytecode[pc]; }, OP_HALT => return, else => unreachable, } }`)}

Each continue :sw expr jumps directly to the switch with a new value, without going through a back-edge of a surrounding loop. The compiler emits a separate dispatch per arm — better branch prediction, fewer indirect jumps.

Why this matters

Modern CPUs predict indirect branches based on the call site. If every iteration of your interpreter loops through the same outer while, there's one indirect branch at the top, and the predictor can only learn one pattern: "next instruction comes from anywhere." With labeled switch and per-arm dispatch, each arm has its own indirect branch, and the predictor learns transitions: "after ADD, the next instruction is often LOAD."

For real interpreters this is typically a 10–30% speedup over the naive loop-around-switch, with no change in semantics.

State machines

The same trick applies to lexers and parsers. Each state is a switch arm; transitions are continue :sw next_state:

${z(`fn lex(input: []const u8) Token { var i: usize = 0; var state: State = .start; sw: switch (state) { .start => { if (i == input.len) return .eof; const c = input[i]; i += 1; switch (c) { ' ', '\\t' => continue :sw .start, 'a'...'z', 'A'...'Z' => continue :sw .ident, '0'...'9' => continue :sw .number, else => return .err, } }, .ident => { // ... read ident chars ... return .ident; }, .number => { // ... read digits ... return .number; }, } }`)}

Compared to a hand-coded computed goto in C, this is type-safe, exhaustive (the compiler still warns about missing arms), and integrated with regular Zig control flow.

Mixing with continue / break of outer loops

Labeled continue and break work as you'd expect when there are nested constructs. You can break :sw value to exit the switch with a value (like a labeled block) instead of jumping arms:

${z(`const result = sw: switch (initial_state) { .a => continue :sw .b, .b => continue :sw .c, .c => break :sw 42, };`)}

This makes a switch into both a dispatch table and a value-producing expression, depending on the arm.

When to use labeled switch

  • You are writing an interpreter, regex engine, or other hot dispatch loop.
  • You have a state machine with frequent transitions between states.
  • Profiling shows the indirect branch on your outer loop is a hot misprediction site.

For ordinary code — a few-dozen-arm switch you hit once per request — a regular switch is fine and clearer. The performance benefit is real but specific.
