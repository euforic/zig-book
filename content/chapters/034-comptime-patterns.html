Beyond generics and reflection, comptime is the right tool for a handful of recurring problems. Recognizing these patterns saves you from reinventing them poorly.

Tables computed at compile time

A lookup table you'd otherwise generate with a script can be built inline:

${z(`const sin_table: [256]f32 = blk: { var t: [256]f32 = undefined; var i: usize = 0; while (i < 256) : (i += 1) { const x = @as(f32, @floatFromInt(i)) * std.math.tau / 256.0; t[i] = std.math.sin(x); } break :blk t; };`)}

The table is computed once during compilation and baked into the binary as a constant. The runtime sees only the result — no startup cost, no separate generator.

Validating string literals

If a function takes a format string or regex or SQL fragment that must be syntactically valid, validate it at comptime:

${z(`fn precompiledRegex(comptime pattern: []const u8) Regex { comptime { validatePattern(pattern) catch |e| @compileError(@errorName(e) ++ " in " ++ pattern); } return Regex.init(pattern); } const re = precompiledRegex("[a-z]+");`)}

Misspell the pattern and the program fails to build, not at runtime. The technique generalizes to anything where the validity of a constant input matters.

Generating switch arms

An inline for over an enum's tags lets you generate switch arms automatically:

${z(`fn handlerName(tag: Event) []const u8 { return switch (tag) { inline else => |t| @tagName(t), }; }`)}

The inline else with a capture is a common idiom: it expands the else branch once per remaining tag, with the tag captured at comptime.

Tagged dispatch without vtables

When you have a tagged union and want different code per variant, the combination of switch and inline lets you keep types specialized:

${z(`const Shape = union(enum) { circle: struct { r: f32 }, rect: struct { w: f32, h: f32 }, triangle: struct { a: f32, b: f32, c: f32 }, }; fn area(s: Shape) f32 { return switch (s) { .circle => |c| std.math.pi * c.r * c.r, .rect => |r| r.w * r.h, .triangle => |t| blk: { const p = (t.a + t.b + t.c) / 2; break :blk @sqrt(p * (p - t.a) * (p - t.b) * (p - t.c)); }, }; }`)}

The compiler knows the payload type in each arm, so accesses are monomorphic. No virtual dispatch, no boxing, no allocation.

Build-mode-aware code

@import("builtin") gives you compile-time facts about the build: target OS, CPU features, optimization mode, etc. Branch on them with regular if — the dead arms are stripped:

${z(`const builtin = @import("builtin"); fn fastSqrt(x: f32) f32 { if (builtin.cpu.arch == .x86_64 and std.Target.x86.featureSetHas(builtin.cpu.features, .sse)) { // use a SIMD intrinsic return @sqrt(x); } else { return @sqrt(x); } } const log_verbose = builtin.mode == .Debug;`)}

This is how the stdlib produces portable code with platform-specific fast paths.

Comptime-only assertions

Sometimes a property must hold or your design breaks. Express it as a comptime check at the top of the file:

${z(`comptime { if (@sizeOf(Header) != 16) @compileError("Header must be exactly 16 bytes"); if (@alignOf(Packet) < 8) @compileError("Packet must be 8-aligned"); }`)}

The check runs once at compile time. If it ever fails, the build breaks with a clear message — orders of magnitude better than a runtime surprise.

Defaulting through comptime

Provide sensible defaults that callers can override, with the override resolved at compile time:

${z(`fn Config(comptime opts: struct { buffer_size: usize = 4096, sync_on_write: bool = false, encoding: Encoding = .utf8, }) type { return struct { // ... use opts.buffer_size, opts.sync_on_write, opts.encoding ... }; } const C = Config(.{ .buffer_size = 8192 });`)}

This is the standard library's pattern: pass an anonymous struct of options where every field has a default. Override only what you need.

What comptime is bad at

Comptime is not the right tool when:

  • The decision is genuinely runtime-only (user input, env vars, file contents at startup).
  • You'd be duplicating a lot of code for each instantiation — the binary gets fat.
  • You want polymorphism with a stable ABI across versions (use a vtable struct instead).

Comptime is a hammer. Most things in your codebase are not nails. Use it where it pays for itself — generics, tables, build-time validation — and leave the rest as ordinary code.
