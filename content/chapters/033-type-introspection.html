Comptime is the door; @typeInfo is the key. Given a type, it returns a tagged union describing that type's structure — fields, variants, parameters, return type, layout. With this, you can write code that adapts itself to whatever type you hand it.

The Type tag

@typeInfo returns std.builtin.Type, a tagged union with a variant per kind of type:

${z(`const std = @import("std"); const T = i32; comptime { const info = @typeInfo(T); switch (info) { .int => |int_info| { std.debug.assert(int_info.signedness == .signed); std.debug.assert(int_info.bits == 32); }, else => @compileError("expected an integer"), } }`)}

The payload of each variant carries the relevant facts: an .int info has signedness and bit width, a .@"struct" info has fields, layout, decls, and a backing integer (for packed), a .@"fn" info has parameters and return type, and so on.

Iterating struct fields

The classic use of typeInfo is generating code per field:

${z(`fn debugPrint(value: anytype) void { const T = @TypeOf(value); const fields = @typeInfo(T).@"struct".fields; std.debug.print("{s}{{\\n", .{@typeName(T)}); inline for (fields) |f| { std.debug.print(" {s}: {any}\\n", .{ f.name, @field(value, f.name) }); } std.debug.print("}}\\n", .{}); }`)}

Each iteration of the inline for bakes in a different f.name as a string literal and a different @field access at compile time.

Common queries

${z(`@typeName(T) // string name, e.g. "main.MyStruct" @hasDecl(T, "init") // does T have a public/private declaration named "init"? @hasField(T, "name") // does T (a struct/union/enum) have a field named "name"? @bitSizeOf(T) // size in bits, including padding @sizeOf(T) // size in bytes @alignOf(T) // alignment in bytes @offsetOf(T, "field") // byte offset of a field within T @field(value, "name") // dynamic field access by string`)}

All of these are comptime — the string arguments must be literals or comptime expressions. There is no runtime reflection.

Building things from typeInfo

You can generate a serializer that handles any struct:

${z(`fn writeJson(writer: anytype, value: anytype) !void { const T = @TypeOf(value); switch (@typeInfo(T)) { .int, .float => try writer.print("{}", .{value}), .bool => try writer.writeAll(if (value) "true" else "false"), .pointer => |p| if (p.size == .slice and p.child == u8) { try writer.print("\\"{s}\\"", .{value}); } else @compileError("can't serialize " ++ @typeName(T)), .@"struct" => |s| { try writer.writeByte('{'); inline for (s.fields, 0..) |f, i| { if (i != 0) try writer.writeByte(','); try writer.print("\\"{s}\\":", .{f.name}); try writeJson(writer, @field(value, f.name)); } try writer.writeByte('}'); }, else => @compileError("unsupported type " ++ @typeName(T)), } }`)}

This is the kind of code that, in other languages, requires macros or runtime reflection or external code generation. In Zig it's a function that happens to be partly comptime.

Creating types programmatically

Zig 0.16 split the old single-builtin @Type into individual type-constructing builtins. To build a struct from a list of fields at comptime:

${z(`// 0.16 idiom: individual type-creating builtins const T = @Struct(.{ .layout = .auto, .fields = &.{ .{ .name = "x", .type = i32, .default_value = null, .is_comptime = false, .alignment = 0 }, .{ .name = "y", .type = i32, .default_value = null, .is_comptime = false, .alignment = 0 }, }, .decls = &.{}, .is_tuple = false, });`)} ${note("Type construction builtins", "

Use the individual type-creating builtins: @Struct, @Enum, @Union, @ErrorSet, @Opaque, and related forms. Each one takes the typed init payload it cares about, which gives clear compile errors when the generated type description is wrong.

")}

Inspecting function types

You can introspect functions too:

${z(`fn arity(comptime F: type) usize { return @typeInfo(F).@"fn".params.len; } fn returnType(comptime F: type) type { return @typeInfo(F).@"fn".return_type.?; } const f: fn (a: i32, b: i32) bool = lessThan; comptime std.debug.assert(arity(@TypeOf(f)) == 2); comptime std.debug.assert(returnType(@TypeOf(f)) == bool);`)}

The shape of stdlib code

Open any stdlib container and you'll see this pattern: type passed in, @typeInfo matched against, branches per shape. Once you're fluent at reading switch-on-typeInfo, large amounts of Zig become legible.
